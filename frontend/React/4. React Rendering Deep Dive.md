# 1. React Rendering Deep Dive

The easiest way to remember React rendering is:

```text
State / Props change
       ↓
     RENDER
       ↓
Reconciliation
       ↓
     COMMIT
       ↓
   DOM update
       ↓
    Browser Paint
```

The key idea:

> **Render = React figures out what should change.**
> **Commit = React applies those changes to the DOM.**

---

## 1. Render vs Commit

### Render Phase

React calls your components to calculate the next UI.

```jsx
function Counter({ count }) {
  console.log("render");

  return <h1>{count}</h1>;
}
```

When `count` changes:

```text
State update
    ↓
React renders Counter
    ↓
React calculates new UI
```

**Important:** Rendering does NOT necessarily mean DOM modification.

---

### Commit Phase

React takes the result of rendering and applies the necessary changes to the actual DOM.

```text
Render
  ↓
" h1 should now contain 5 "
  ↓
Commit
  ↓
DOM becomes <h1>5</h1>
```

### Interview memory trick

> **Render = THINK**
> **Commit = DO**

React first decides what the UI should look like, then commits the required DOM changes.

---

## 2. Reconciliation

Reconciliation is the process React uses to determine:

> **"What changed between the previous UI and the new UI?"**

Example:

```jsx
// Previous
<h1>Hello</h1>

// New
<h1>Hello Aashir</h1>
```

React doesn't throw away the entire DOM.

It determines that only the text changed and updates that part.

```text
Previous Tree
     ↓
New Tree
     ↓
Compare
     ↓
Find differences
     ↓
Commit minimal necessary DOM changes
```

### Keys are important

Consider:

```jsx
users.map(user => (
  <User key={user.id} user={user} />
))
```

Keys help React identify which list item is which across renders.

Bad:

```jsx
key={index}
```

when the list can be reordered/inserted/deleted.

### Interview question

**Q: Does React compare the entire DOM every time?**

**Answer:**

> No. React creates a new element tree during rendering and reconciles it with the previous tree to determine the necessary updates. It then commits the required DOM changes rather than rebuilding the entire DOM.

---

# 3. Fiber

Fiber is React's internal architecture for managing rendering work.

Don't overcomplicate this.

Think:

> **Fiber allows React to break rendering work into smaller units and manage that work intelligently.**

Before Fiber, React's rendering work was more difficult to interrupt.

With Fiber, React can conceptually:

```text
Start rendering
      ↓
Do some work
      ↓
Pause if necessary
      ↓
Handle higher-priority work
      ↓
Continue later
```

This becomes important for:

* concurrent rendering
* prioritizing updates
* responsiveness
* Suspense
* transitions

### Memory trick

> **Fiber = React's work manager**

You generally don't need to memorize Fiber's internal data structure for a senior interview.

---

# 4. Batching

Batching means React groups multiple state updates together and performs fewer renders.

Example:

```jsx
function handleClick() {
  setCount(c => c + 1);
  setName("Aashir");
  setOpen(true);
}
```

Instead of:

```text
setCount → render
setName  → render
setOpen  → render
```

React can batch them:

```text
setCount
setName
setOpen
   ↓
one render
```

### Why?

To avoid unnecessary rendering work.

---

### Important: Functional updates

When multiple updates depend on the previous state:

```jsx
setCount(c => c + 1);
setCount(c => c + 1);
```

React can correctly apply both updates.

Result:

```text
count + 2
```

Don't do:

```jsx
setCount(count + 1);
setCount(count + 1);
```

because both updates may use the same captured `count`.

---

### Senior interview question

**Q: Does React 18 batch updates outside event handlers?**

Yes. Modern React performs automatic batching in more situations, including updates from promises, timers, and other async contexts.

The important interview concept is:

> **React batches compatible state updates to reduce unnecessary renders.**

# 5. Strict Mode

`StrictMode` is a development-time tool that helps identify potential problems.

```jsx
<StrictMode>
  <App />
</StrictMode>
```

One thing that often confuses developers:

In development, React may intentionally invoke certain logic more than once.

For example:

```jsx
useEffect(() => {
  console.log("effect");
}, []);
```

You may see behavior that looks like:

```text
render
render
effect
cleanup
effect
```

This is intentional development behavior.

### Why?

To expose bugs such as:

* missing cleanup
* impure rendering
* unsafe side effects
* assumptions that code runs only once

### Important

Strict Mode does **not** mean:

> "React renders twice in production."

It's primarily a development-time check.

### Interview question

**Q: Why does `useEffect` run twice in development?**

Good answer:

> With Strict Mode, React intentionally performs additional development checks, including an extra setup/cleanup cycle for effects, to help expose side-effect and cleanup bugs. This behavior should not be interpreted as normal production behavior.

# 6. Concurrent Rendering

This is probably the most confusing topic, so keep the mental model simple.

Concurrent rendering means React can work on rendering without necessarily blocking everything until that work finishes.

Think:

```text
Urgent update
    ↓
Handle quickly

Non-urgent update
    ↓
Can be interrupted
    ↓
Continue later
```

Example:

```jsx
startTransition(() => {
  setSearchResults(results);
});
```

You're telling React:

> "This update is less urgent."

For example:

```text
Typing in search box
       ↓
URGENT
       ↓
Update input immediately

Filtering 10,000 results
       ↓
NON-URGENT
       ↓
Can be deprioritized
```

This helps keep the UI responsive.

---

# `startTransition`

Example:

```jsx
const [query, setQuery] = useState("");
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  const value = e.target.value;

  setQuery(value);

  startTransition(() => {
    setSearchQuery(value);
  });
}
```

Here:

```text
setQuery
   ↓
urgent

setSearchQuery
   ↓
transition / lower priority
```

### Interview question

**Q: Does concurrent rendering mean JavaScript runs on multiple threads?**

**No.**

This is a common trap.

Concurrent rendering is primarily about **React being able to schedule, prioritize, pause, and resume rendering work**. It doesn't mean React components are executing simultaneously on multiple JavaScript threads.

# Senior Interview Questions

These are the questions I'd make sure you can answer without notes.

### Fundamental

**1. What is the difference between render and commit?**

> Render calculates what the UI should look like. Commit applies the necessary changes to the DOM.

**2. Does a render always cause a DOM update?**

> No. React may render a component but determine that there are no relevant DOM changes to commit.

**3. What is reconciliation?**

> The process of comparing the new React element tree with the previous one to determine what needs to change.

**4. Why are keys important in React lists?**

> They provide stable identity so React can correctly match elements between renders, especially when items are inserted, removed, or reordered.

---

### Senior-level

**5. What is Fiber?**

> Fiber is React's internal rendering architecture that represents rendering work as units that React can schedule and prioritize.

**6. What is batching? Why does React do it?**

> Batching groups multiple state updates so React can process them together, reducing unnecessary renders and improving performance.

**7. Why does Strict Mode appear to run things twice?**

> React intentionally performs additional development checks to expose impure rendering and missing effect cleanup.

**8. What is concurrent rendering?**

> It allows React to schedule rendering work according to priority and potentially interrupt lower-priority work to keep the UI responsive.

**9. Does concurrent rendering use multiple JavaScript threads?**

> No. It's primarily a scheduling model within React's rendering system, not multithreaded component execution.

**10. When would you use `startTransition`?**

> For non-urgent UI updates, such as updating expensive search results or filtering a large dataset while keeping user input responsive.

---

# The 30-Second Interview Answer

If an interviewer asks:

> **"Explain how React rendering works."**

You can say:

> "When state or props change, React renders the component tree to calculate the next UI. It then reconciles the new tree with the previous one to determine what actually changed. Fiber manages this rendering work and allows React to schedule and prioritize it. After reconciliation, React enters the commit phase and applies the necessary DOM changes. React also batches updates to reduce unnecessary renders, while concurrent rendering allows lower-priority work to be interrupted so urgent interactions remain responsive."

That's the level I'd target for you: **understand the mechanics well enough to reason about performance and architecture, without getting lost in React internals.**
