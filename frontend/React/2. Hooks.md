# React Performance — What You Actually Need to Understand

Before individual optimizations, you need one mental model:

```text
                USER ACTION
                    ↓
              State update
                    ↓
             React schedules
                    ↓
              Component renders
                    ↓
        ┌───────────┴───────────┐
        ↓                       ↓
   Component work         Child component work
        ↓                       ↓
 expensive calculation    expensive calculation
        ↓                       ↓
             React reconciliation
                    ↓
               DOM commit
                    ↓
              Browser rendering
                    ↓
                  SCREEN
```

A performance problem means **too much work is happening somewhere in this pipeline**.

The rest of React Performance is basically learning how to answer:

> **Which work is unnecessary, which work is expensive, and which work can be delayed?**

---

# 1. Unnecessary Re-renders

This is where we should start because everything else builds on it.

## The problem

Imagine:

```tsx
function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <UserList users={users} />
    </>
  );
}
```

When you click the button:

```text
setCount()
   ↓
App renders again
   ↓
UserList is evaluated again
```

But `UserList` doesn't care about `count`.

So you might have:

```text
count changed
   ↓
App needs to render
   ↓
UserList doesn't actually need new UI
   ↓
but React may still render it
```

That's the **unnecessary work** we're interested in.

---

## Important distinction

Don't think:

> Parent renders → every child DOM gets updated.

That's wrong.

Think:

```text
Parent renders
      ↓
React evaluates children
      ↓
React compares resulting UI
      ↓
Only necessary DOM changes are committed
```

So there are different kinds of work:

```text
Component execution
       ↓
Reconciliation
       ↓
DOM update
```

They are not the same thing.

### Interview question

**"Does a React re-render mean the DOM is updated?"**

Answer:

> No. A re-render means React executes the component and calculates the next UI. During reconciliation, React determines what actually changed, and the commit phase applies only the necessary DOM updates.

That's a foundational senior answer.

---

# 2. React.memo

Now we have a problem:

```text
Parent renders
      ↓
Child renders
      ↓
Child didn't actually need to render
```

React gives us:

```tsx
const UserList = React.memo(function UserList({ users }) {
  ...
});
```

The mental model is:

```text
Parent renders
      ↓
Should UserList render?
      ↓
Compare previous props
with new props
      ↓
Same?
 ┌────┴────┐
YES       NO
 ↓         ↓
bailout   render
```

So `React.memo` is essentially a **bailout optimization**.

---

# But now comes the important part

Suppose:

```tsx
<UserList
  users={users}
/>
```

and `users` hasn't changed.

Fine.

But suppose:

```tsx
<UserList
  filters={{ status: "active" }}
/>
```

Every time the parent renders:

```tsx
{ status: "active" }
```

creates a **new object**.

So:

```text
Render 1
filters → Object A

Render 2
filters → Object B
```

Even though:

```text
Object A contents
=
Object B contents
```

the references are different:

```text
Object A !== Object B
```

Therefore the memoized child sees the prop as changed.

This is where **referential equality** becomes critical.

---

# 3. Referential Equality

This is something you should understand rather than memorize.

JavaScript objects are references.

```tsx
const a = { name: "Aashir" };
const b = { name: "Aashir" };
```

This is:

```tsx
a === b // false
```

Because:

```text
a → Object #1

b → Object #2
```

Same content does not mean same reference.

But:

```tsx
const a = { name: "Aashir" };
const b = a;

a === b // true
```

Now:

```text
a ─────┐
       ↓
    Object #1
       ↑
       └──── b
```

This is extremely important for React performance because props can be:

* objects
* arrays
* functions

and all of these are reference values.

# 4. useMemo

Now imagine this:

```tsx
const filteredUsers = users
  .filter(...)
  .sort(...)
  .map(...);
```

Suppose:

```text
users = 100,000
```

and the component renders 50 times.

You might be doing:

```text
expensive calculation
expensive calculation
expensive calculation
...
50 times
```

If the calculation doesn't need to happen again when its inputs haven't changed, we can memoize the result:

```tsx
const filteredUsers = useMemo(() => {
  return users
    .filter(...)
    .sort(...)
    .map(...);
}, [users]);
```

Mental model:

```text
First render
     ↓
calculate
     ↓
store result

Next render
     ↓
Did users change?
   ↙       ↘
 NO        YES
 ↓          ↓
reuse     calculate
```

That is the **real reason** for `useMemo`.

---

# But useMemo has another important use

Suppose:

```tsx
const filters = {
  status,
  category
};
```

You might use:

```tsx
const filters = useMemo(() => ({
  status,
  category
}), [status, category]);
```

Now you're not necessarily trying to avoid an expensive calculation.

You're trying to maintain a **stable object reference**.

That can become useful with:

```text
useMemo
   ↓
stable object reference
   ↓
React.memo
   ↓
child can potentially bail out
```

This relationship is exactly the kind of thing a senior interviewer may test.

---

# 5. Why NOT useMemo everywhere?

This is where senior-level reasoning starts.

Someone says:

> "I'll use useMemo everywhere for performance."

That's not a strong answer.

Ask:

```text
How expensive is the calculation?
How frequently does it run?
How often do dependencies change?
How much does memoization cost?
Does the optimization actually solve a measured problem?
```

For:

```tsx
const fullName = firstName + " " + lastName;
```

using `useMemo` is generally unnecessary.

You're potentially doing:

```text
dependency checking
+
cache management
+
more code complexity
```

to avoid:

```text
string concatenation
```

So remember:

> **Memoization itself has a cost.**

The goal isn't:

> "Use memoization."

The goal is:

> **"Avoid meaningful unnecessary work."**

---

# 6. useCallback

Now functions.

Consider:

```tsx
function Parent() {
  const handleClick = () => {
    console.log("clicked");
  };

  return <Child onClick={handleClick} />;
}
```

Every render creates another function:

```text
Render 1 → function A

Render 2 → function B

Render 3 → function C
```

Therefore:

```text
function A !== function B
```

If:

```tsx
const Child = React.memo(...)
```

then the child sees:

```text
previous onClick
        ≠
new onClick
```

So it can render again.

`useCallback` allows you to preserve that function reference:

```tsx
const handleClick = useCallback(() => {
  console.log("clicked");
}, []);
```

Mental model:

```text
render
 ↓
useCallback
 ↓
same function reference
 ↓
until dependencies change
```

---

# 7. useMemo vs useCallback

This should become automatic:

```text
useMemo
   ↓
remember a VALUE

useCallback
   ↓
remember a FUNCTION
```

Conceptually:

```tsx
useMemo(() => expensiveCalculation(), deps);

useCallback(() => doSomething(), deps);
```

And actually, you can think of `useCallback` conceptually as related to:

```tsx
useMemo(() => function, deps)
```

The important distinction is **what you're trying to stabilize**.

---

# 8. Large Lists

Now consider a completely different problem.

You have:

```text
100,000 users
```

and render:

```tsx
users.map(user => <UserRow user={user} />)
```

You can optimize individual rows with `React.memo`.

But you still have:

```text
100,000 components
100,000 DOM nodes
```

That's potentially a huge amount of work.

This is where **virtualization** comes in.

Instead of:

```text
100,000 records
      ↓
100,000 DOM elements
```

you do:

```text
100,000 records
      ↓
┌──────────────────────┐
│ visible viewport     │
│                      │
│ Row 1                │
│ Row 2                │
│ ...                  │
│ Row 20               │
└──────────────────────┘
```

Only the rows around the viewport are rendered.

As you scroll:

```text
rows leaving viewport
        ↓
remove/reuse

rows entering viewport
        ↓
render
```

This is called **virtualization/windowing**.

### Important interview distinction

`React.memo`:

> Avoid unnecessary rendering of existing components.

Virtualization:

> Avoid having thousands of off-screen components/DOM nodes in the first place.

Those solve different problems.

# 9. Debouncing

Now imagine:

```tsx
<input onChange={handleSearch} />
```

User types:

```text
R
Re
Rea
Reac
React
```

Without debounce:

```text
R      → API
Re     → API
Rea    → API
Reac   → API
React  → API
```

With debounce:

```text
R
Re
Rea
Reac
React
      ↓
wait for inactivity
      ↓
API
```

Mental model:

> **Debounce = wait until the activity stops.**

Common use:

```text
search
autocomplete
validation
```

---

# 10. Throttling

For something like scroll:

```text
scroll
scroll
scroll
scroll
scroll
scroll
...
```

You don't necessarily want to process every event.

Throttle:

```text
scroll → execute
scroll → skip
scroll → skip
scroll → execute
scroll → skip
...
```

Mental model:

> **Throttle = control how frequently something can execute.**

---

# 11. Code Splitting

Now we're solving another completely different problem.

Maybe your React application has:

```text
Dashboard
Admin
Reports
Analytics
Settings
Editor
```

Why download all of that JavaScript before the user even opens those features?

Instead:

```text
Initial bundle
     ↓
Dashboard
     ↓
User opens Reports
     ↓
Load Reports chunk
```

This is **code splitting**.

The goal is to reduce:

```text
initial JavaScript
```

which means potentially less:

```text
download
parse
compile
execute
```

---

# 12. Browser Rendering

Even if React is optimized, the browser can still be slow.

After React commits:

```text
DOM changes
     ↓
Style calculation
     ↓
Layout
     ↓
Paint
     ↓
Composite
```

So imagine:

```text
React rendering = 5ms
Browser rendering = 100ms
```

Adding `useMemo` isn't going to fix the main problem.

This is why senior engineers need to understand the browser side too.

---

# 13. Profiling

This ties everything together.

If someone says:

> "The page is slow."

You shouldn't immediately say:

> "Let's add useMemo."

Instead:

```text
Page is slow
     ↓
Profile
     ↓
Where is the time going?
```

Maybe:

```text
API       → 800ms
React     → 20ms
Browser   → 10ms
```

Then React optimization isn't your main problem.

Or:

```text
API       → 50ms
React     → 500ms
Browser   → 100ms
```

Now you investigate rendering.

Or:

```text
Initial JS → 3MB
```

Now you're looking at bundle/code splitting.

**This is the senior mental model.**

# What an interviewer is really testing

They aren't really testing whether you remember:

```text
React.memo
useMemo
useCallback
```

They're testing whether you can reason:

### Scenario

> "A page contains a search box and a large list. Every time I type, the UI becomes sluggish. How would you approach it?"

You should mentally go:

```text
Typing
  ↓
state update
  ↓
component render
  ↓
large list renders
  ↓
expensive filtering?
  ↓
large DOM?
  ↓
unnecessary child renders?
```

Then possible solutions:

```text
expensive calculation
       → useMemo

unnecessary child rendering
       → React.memo

unstable function props
       → useCallback

huge DOM
       → virtualization

input triggering too many requests
       → debounce

expensive UI update blocking typing
       → useTransition / useDeferredValue
```

**Notice the difference.**

You're not memorizing:

> "`useMemo` = performance."

You're understanding:

> **"I have identified an expensive calculation that repeats unnecessarily, therefore memoization may be appropriate."**

That is the level we should use for your interview preparation.

And I would go **this deep for each major React Performance concept**, rather than giving you another outline.
