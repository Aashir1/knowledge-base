
# React Performance

## 1. The core problem

React performance problems usually come down to one thing:

> **We're making the browser or JavaScript engine do more work than necessary.**

Think about this flow:

```text
User clicks / types
       ↓
State update
       ↓
React renders
       ↓
Components execute
       ↓
Calculations happen
       ↓
React commits DOM changes
       ↓
Browser renders
```

Performance problems can happen at **any point**.

For example:

```text
State update
     ↓
Parent renders
     ↓
100 children render
     ↓
Each child performs expensive calculation
     ↓
Browser processes large DOM
     ↓
UI feels slow
```

The senior-level question isn't:

> "Which React optimization should I use?"

It's:

> **"Where is the actual bottleneck?"**

---

# 2. Re-render ≠ DOM update

This is the first thing you need to be very clear about.

Suppose:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  return <div>{count}</div>;
}
```

You call:

```tsx
setCount(1);
```

React doesn't simply say:

```text
state changed
↓
change DOM
```

Conceptually:

```text
setCount(1)
    ↓
schedule update
    ↓
render component
    ↓
calculate new UI
    ↓
reconcile
    ↓
commit required DOM changes
```

So:

### Re-render

Means React executes the component again to determine what the UI should look like.

### DOM update

Means React actually changes something in the browser DOM.

Therefore:

```text
Re-render
   ≠
DOM update
```

A component can re-render while React ultimately makes little or no DOM change.

---

# 3. Where unnecessary work comes from

Imagine:

```tsx
function Parent() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <ExpensiveChild />
    </>
  );
}
```

When `count` changes:

```text
Parent state changes
       ↓
Parent renders
       ↓
ExpensiveChild is evaluated too
```

Even though `ExpensiveChild` doesn't care about `count`.

This is where performance optimization becomes relevant.

The question becomes:

> Can React skip work that doesn't need to happen?

That's where `React.memo` comes in.

---

# 4. React.memo mental model

```tsx
const ExpensiveChild = React.memo(function ExpensiveChild() {
  // expensive rendering
});
```

Think:

```text
Parent renders
      ↓
Should Child render?
      ↓
Are Child's props effectively unchanged?
      ↓
YES
      ↓
Potentially skip Child rendering
```

So `React.memo` is essentially a **bailout mechanism**.

It tells React:

> "If this component receives the same props, you can reuse the previous rendered result instead of rendering it again."

But there is an important catch.

---

# 5. Referential equality

Consider:

```tsx
function Parent() {
  const user = {
    name: "Aashir"
  };

  return <Child user={user} />;
}
```

Every time `Parent` renders:

```text
render #1 → user → object A
render #2 → user → object B
render #3 → user → object C
```

Even though the contents are the same:

```text
object A !== object B
```

Because they're different references.

This matters because React's prop comparison is based on shallow/reference equality for typical `memo` usage.

So:

```tsx
<Child user={{ name: "Aashir" }} />
```

can defeat the benefit of:

```tsx
React.memo(Child)
```

because the prop reference keeps changing.

---

# 6. This is where useMemo and useCallback connect

Suppose:

```tsx
const Child = React.memo(({ user }) => {
  ...
});
```

Parent:

```tsx
function Parent() {
  const user = {
    name: "Aashir"
  };

  return <Child user={user} />;
}
```

You could stabilize the object:

```tsx
const user = useMemo(() => ({
  name: "Aashir"
}), []);
```

Now:

```text
Parent render
     ↓
useMemo
     ↓
same object reference
     ↓
React.memo
     ↓
Child can potentially bail out
```

Similarly:

```tsx
const handleClick = () => {};
```

creates a new function reference on every render.

`useCallback` can stabilize that reference.

So the relationship is:

```text
React.memo
     ↑
     │
needs stable props
     ↑
     │
 ┌───┴────┐
useMemo  useCallback
```

But **don't conclude that you should always use them**.

---

# 7. Why not useMemo everything?

Because memoization isn't free.

Conceptually:

```text
Without useMemo

calculate value
```

versus:

```text
With useMemo

check dependencies
↓
maintain cached value
↓
return cached value
```

If the calculation is extremely cheap:

```tsx
const fullName = firstName + " " + lastName;
```

memoizing it may be pointless.

You've introduced complexity and overhead to avoid almost no work.

The senior mindset is:

> **Optimize meaningful work, not every piece of work.**

---

# 8. Expensive computation

Consider:

```tsx
const filteredUsers = users
  .filter(...)
  .sort(...)
  .map(...);
```

If you have:

```text
10 users
```

probably not a problem.

But:

```text
500,000 users
```

and this runs on every render?

Now you have a real performance problem.

You need to ask:

```text
Why is this calculation running?
How frequently?
How expensive is it?
Does it actually need to run?
```

Then `useMemo` may make sense.

---

# 9. Large lists

Another common performance problem:

```text
100,000 items
       ↓
100,000 React elements
       ↓
100,000 DOM nodes
```

Even if React renders efficiently, the browser still has a huge amount of work.

This is where **virtualization** helps.

Instead of:

```text
100,000 items
     ↓
render 100,000
```

you do:

```text
100,000 items
     ↓
viewport
     ↓
render only visible ~20 items
```

As the user scrolls:

```text
remove items leaving viewport
add items entering viewport
```

So virtualization attacks a completely different problem from `useMemo`.

---

# 10. Debouncing

Imagine search:

```text
R
Re
Rea
Reac
React
```

Without debouncing:

```text
R     → API
Re    → API
Rea   → API
Reac  → API
React → API
```

Five requests.

With debounce:

```text
R
Re
Rea
Reac
React
     ↓
wait until typing pauses
     ↓
API
```

Mental model:

> **Debounce = wait until activity stops.**

Common use cases:

* search
* autocomplete
* form validation

---

# 11. Throttling

Suppose scroll fires hundreds of events:

```text
scroll
scroll
scroll
scroll
scroll
scroll
...
```

Instead of processing every event:

```text
scroll → execute
scroll → ignore
scroll → ignore
scroll → execute
...
```

Mental model:

> **Throttle = limit how often something can execute.**

Common use cases:

* scroll
* resize
* mouse movement

---

# 12. Code splitting

Another performance problem happens before React even renders much:

```text
Huge JavaScript bundle
       ↓
download
       ↓
parse
       ↓
compile
       ↓
execute
```

Instead of loading everything immediately:

```text
Initial bundle
      ↓
Application loads
      ↓
User opens Admin
      ↓
Admin code downloaded
```

This is **code splitting**.

It reduces the amount of JavaScript required upfront.

---

# 13. Browser rendering

React isn't the entire performance story.

After React commits changes:

```text
React
 ↓
DOM
 ↓
Style calculation
 ↓
Layout
 ↓
Paint
 ↓
Composite
```

For example, changing something that requires layout can cause more browser work than simply changing a property that can be composited efficiently.

So senior frontend performance isn't:

```text
React = performance
```

It's:

```text
React
+
JavaScript
+
DOM
+
Browser rendering
+
Network
+
Bundle
```

---

# 14. Profiling — the senior mindset

This is probably the most important part.

Imagine someone says:

> "The page is slow. Add useMemo."

That's not a strong senior answer.

A better approach:

```text
Page is slow
     ↓
Measure
     ↓
Profile
     ↓
Find bottleneck
     ↓
Understand cause
     ↓
Choose optimization
     ↓
Measure again
```

You might discover:

```text
React rendering = 10ms
API = 700ms
```

Then `useMemo` isn't going to solve the main problem.

Or:

```text
API = 50ms
React rendering = 600ms
```

Now React rendering deserves investigation.

# Senior-level questions

### Q1. What is the difference between a re-render and a DOM update?

**Answer:**

A re-render means React executes the component again to determine the next UI representation. After reconciliation, React only commits the DOM changes that are actually necessary. Therefore, every re-render does not necessarily result in a DOM update.

---

### Q2. When would you use React.memo?

**Answer:**

I'd use it when a component renders frequently due to its parent updating, but its output usually remains the same when its props haven't changed. `React.memo` allows React to potentially bail out of rendering that child. I'd first profile or identify that the repeated rendering is meaningful enough to optimize.

---

### Q3. Why doesn't React.memo always prevent re-renders?

Because the props may change by reference.

For example:

```tsx
<Child user={{ name: "Aashir" }} />
```

creates a new object on each parent render.

Therefore:

```text
previous user !== new user
```

and the memoized child may render again.

---

### Q4. What's the relationship between React.memo and useCallback?

`React.memo` can prevent a child from rendering when its props haven't changed.

But functions created inside the parent get a new reference on each render.

So:

```tsx
const handleClick = () => {};
```

can cause a memoized child receiving `handleClick` to see a changed prop.

`useCallback` can preserve the function reference when its dependencies haven't changed.

---

### Q5. When should you NOT use useMemo?

When the calculation is cheap, the component doesn't render frequently, or profiling doesn't indicate that the calculation is a meaningful bottleneck.

`useMemo` has its own memory/dependency-management overhead and adds complexity.

---

### Q6. Is useMemo a guarantee that React will never recalculate the value?

No.

It's a performance optimization, not a semantic guarantee that the value will always remain cached forever. Code should remain correct even without relying on the cache.

---

### Q7. What's the difference between useMemo and useCallback?

Simple mental model:

```text
useMemo
   ↓
memoize a VALUE

useCallback
   ↓
memoize a FUNCTION
```

Conceptually:

```tsx
useMemo(() => expensiveCalculation(), [deps])

useCallback(() => doSomething(), [deps])
```

---

### Q8. How would you investigate a slow React page?

I'd first measure rather than immediately optimize.

I'd look at:

```text
React Profiler
Browser Performance tools
Network
CPU usage
Memory
Bundle size
```

Then identify whether the bottleneck is:

```text
rendering
computation
DOM
browser layout/paint
network
JavaScript bundle
```

Then apply the optimization appropriate to that bottleneck and measure again.

---

### Q9. How would you optimize a list containing 100,000 rows?

First I'd determine whether all rows need to be rendered simultaneously.

If the user only sees a small portion, I'd consider **virtualization**, so only visible or near-visible rows are mounted.

I'd also look at row rendering cost, unnecessary re-renders, data fetching, and DOM complexity.

---

### Q10. Debounce vs throttle?

```text
Debounce
→ execute after activity stops

Throttle
→ execute at controlled intervals
```

For example:

```text
Search input → debounce
Scroll event → throttle
```

---

### Q11. Does useTransition make expensive JavaScript execute faster?

No.

It doesn't make the computation itself faster.

It allows React to treat certain updates as lower priority so urgent interactions can remain responsive.

---

### Q12. Does useDeferredValue debounce a value?

No.

Debouncing is time-based:

```text
wait X milliseconds
```

`useDeferredValue` is about React rendering priority:

```text
latest value
     ↓
deferred version may temporarily lag
```

# Quick revision

Remember these:

```text
Re-render ≠ DOM update

React.memo
→ can skip unnecessary child rendering

useMemo
→ memoize a value/calculation

useCallback
→ stabilize function reference

Referential equality
→ important for memoization

Virtualization
→ don't render 100,000 DOM nodes if only 20 are visible

Debounce
→ wait until activity stops

Throttle
→ limit execution frequency

Code splitting
→ reduce initial JavaScript

Browser performance
→ React isn't the whole story

Profiling
→ measure first, optimize second
```

## The senior-level mental model

If the interviewer gives you:

> **"This React page is slow. How would you optimize it?"**

Don't immediately list `useMemo`, `useCallback`, and `React.memo`.

Think:

```text
                 Page is slow
                      ↓
                   PROFILE
                      ↓
             Where is the cost?
                      ↓
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
    React           JS/CPU        Browser
   renders       computation       / DOM
       ↓              ↓              ↓
 React.memo        useMemo       virtualization
 stable props      algorithm     reduce DOM
                   ↓              ↓
             ┌──────┴──────┐
             ↓             ↓
          Network       Bundle
             ↓             ↓
         caching       code split
         batching      lazy load
```

**That's the level I want you to reach for senior interviews:** not *"I know performance APIs"*, but **"I can identify the type of work that's expensive and choose an optimization based on the bottleneck."**
