The goal is not just to memorize React definitions. The goal is:

> **Understand what is happening → build a mental model → connect it to real code → then learn how to explain it in an interview.**

# 1. Core React — Deep Understanding

We'll start with the most important concept:

## React Rendering & Mental Model

Before hooks, memoization, performance, etc., you need to understand **what actually happens when React renders**.

---

# 1. Problem

Suppose we have:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>{count}</h1>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </div>
  );
}
```

When we click:

```text
Click button
    ↓
setCount(1)
    ↓
???
```

What exactly happens?

Does React:

```text
change <h1> directly?
```

Or:

```text
run Counter() again?
```

Or:

```text
rebuild the entire DOM?
```

Understanding this is the foundation for many senior React questions.

---

# 2. Why the normal mental model becomes a problem

A common beginner mental model is:

> "When state changes, React changes the DOM."

That's **too simplified**.

A better mental model is:

```text
State changes
     ↓
React schedules an update
     ↓
Component renders again
     ↓
React calculates what changed
     ↓
React commits necessary DOM changes
```

The important distinction is:

> **Rendering is not the same thing as updating the DOM.**

This distinction comes up everywhere in React performance discussions.

---

# 3. Core mental model 🧠

Think of React as having **two major stages**:

```text
              STATE UPDATE
                   ↓
          ┌─────────────────┐
          │     RENDER      │
          │                 │
          │ "What should    │
          │  the UI look    │
          │  like now?"     │
          └────────┬────────┘
                   ↓
          ┌─────────────────┐
          │     COMMIT      │
          │                 │
          │ "Apply required  │
          │  changes to DOM"│
          └─────────────────┘
                   ↓
                Browser
```

### Render phase

React calls your components and figures out:

> **What should the UI look like?**

### Commit phase

React takes the result and applies the necessary changes to the actual DOM.

---

# 4. Small example

Consider:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  console.log("Counter rendered");

  return (
    <div>
      <h1>{count}</h1>

      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </div>
  );
}
```

Initially:

```text
count = 0
```

React renders:

```html
<h1>0</h1>
```

Then user clicks the button.

```text
setCount(1)
     ↓
React schedules update
     ↓
Counter() runs again
     ↓
count = 1
```

React now gets:

```html
<h1>1</h1>
```

React compares the previous result:

```text
Previous:
<h1>0</h1>

New:
<h1>1</h1>
```

It determines that the text needs to change.

Then during commit:

```text
DOM:
<h1>0</h1>

        ↓

<h1>1</h1>
```

It **doesn't throw away the entire DOM and rebuild everything**.

---

# 5. What happens internally

Let's build the complete mental model.

```text
User clicks
     ↓
setCount(1)
     ↓
React schedules update
     ↓
Render phase
     ↓
Counter() runs
     ↓
New React element tree
     ↓
Reconciliation
     ↓
React determines differences
     ↓
Commit phase
     ↓
DOM changes
```

### Important terminology

You will hear these words in interviews:

**Render**

React executes components to determine the next UI.

**Reconciliation**

React compares the previous rendered result with the new result to determine what needs to change.

**Commit**

React applies the required changes to the DOM.

---

# 6. Very important: Re-render ≠ DOM update

This is one of the most important things to remember.

Suppose:

```tsx
function App() {
  const [count, setCount] = useState(0);

  return <h1>{count}</h1>;
}
```

When:

```tsx
setCount(1);
```

happens:

```text
App renders again
        ↓
React calculates new UI
        ↓
DOM actually changes
```

But if the rendered output produces no meaningful DOM difference:

```text
Component renders
       ↓
React compares
       ↓
No DOM change required
```

So:

> **A component re-rendering does not automatically mean the browser DOM changed.**

This is extremely important when we later discuss:

* `React.memo`
* `useMemo`
* `useCallback`
* performance optimization

---

# 7. Common confusion

## Confusion #1: "React renders the DOM"

Not exactly.

Your component:

```tsx
function App() {
  return <h1>Hello</h1>;
}
```

returns a **React element description**.

Conceptually:

```text
Component
   ↓
React elements
   ↓
Reconciliation
   ↓
DOM
```

The component isn't directly manipulating the DOM.

---

## Confusion #2: "Re-render means the whole page redraws"

No.

A component may execute again:

```tsx
function App() {
  console.log("render");

  return ...
}
```

without React changing every DOM node.

React determines which changes actually need to be committed.

---

## Confusion #3: "Virtual DOM is a copy of the browser DOM"

Don't think of it as:

```text
Browser DOM
      ↓
exact clone
```

A better mental model:

> React maintains an in-memory representation of the UI and uses it to determine what changes need to be committed to the actual DOM.

# 8. Senior interview questions

### Q1. What causes a React component to re-render?

We'll go deeper into this separately, but the major causes include:

```text
State update
   ↓
component re-render

Parent re-render
   ↓
child may re-render

Context value changes
   ↓
consuming components re-render

External store update
   ↓
subscribed components re-render
```

---

### Q2. Does re-render mean DOM update?

**No.**

A re-render means React executes the component and calculates the next UI. React then determines whether an actual DOM change is necessary during reconciliation/commit.

---

### Q3. What is reconciliation?

A good interview explanation:

> Reconciliation is the process React uses to compare the previous rendered element tree with the new one and determine what changes are necessary before committing them to the DOM.

---

### Q4. Render phase vs commit phase?

Think:

```text
RENDER
"What should the UI look like?"

        ↓

COMMIT
"Apply those changes to the DOM."
```

---

# 🎯 30-second interview answer

> **When a state update occurs, React schedules an update and re-renders the affected component tree. During the render phase, React executes the components and produces the next UI representation. It then reconciles the previous and new results to determine what actually changed. During the commit phase, React applies the necessary changes to the DOM. So a re-render doesn't necessarily mean the entire DOM is updated.**
