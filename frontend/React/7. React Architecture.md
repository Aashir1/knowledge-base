At senior level, this topic is less about “where do I put this component?” and more about **how do I keep a React application maintainable as it grows?**

### 1. The mental model

Think of a large React app in layers:

```text
UI
 ↓
Components
 ↓
Feature / Business Logic
 ↓
State + Data Fetching
 ↓
API / Services
 ↓
Backend
```

A good architecture keeps these responsibilities separated.

---

## 2. Feature-based structure

Instead of organizing everything by file type:

```text
components/
hooks/
services/
pages/
utils/
```

Prefer grouping by **business feature**:

```text
src/
├── features/
│   ├── appointments/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api.ts
│   │   ├── types.ts
│   │   └── utils.ts
│   │
│   ├── users/
│   └── notifications/
│
├── components/
│   ├── Button/
│   ├── Modal/
│   └── Table/
│
├── lib/
│   ├── api-client.ts
│   └── auth.ts
│
└── app/
```

### Why?

Imagine `appointments` has:

* 8 components
* 3 hooks
* 5 API calls
* appointment-specific types
* validation
* business rules

Keeping them together makes the feature easier to understand, modify, and eventually remove.

**Senior principle:**

> Organize around business capabilities, not technical file types.

---

# 3. Smart vs Dumb Components

You may hear:

> Container vs Presentational components

Older React architecture heavily emphasized this distinction.

Modern React doesn't require strict separation, but the underlying idea is still useful.

### Presentational

Focuses mainly on UI:

```tsx
<AppointmentCard
  appointment={appointment}
  onCancel={handleCancel}
/>
```

It doesn't need to know:

* where data came from
* how API calls work
* authentication
* cache invalidation

### Feature/container component

Handles business behavior:

```tsx
function AppointmentList() {
  const { data } = useAppointments();

  const cancelAppointment = useCancelAppointment();

  return (
    <AppointmentTable
      appointments={data}
      onCancel={cancelAppointment}
    />
  );
}
```

### Memory trick

> **UI component = how it looks**
> **Feature logic = what it does**

Don't force every component into one category. Use the separation when complexity justifies it.

---

# 4. Custom Hooks = Logic Reuse

Instead of putting business logic directly into components:

```tsx
function AppointmentPage() {
  // 100 lines of fetching,
  // validation,
  // transformations...
}
```

extract reusable behavior:

```tsx
function useAppointments(filters) {
  return useQuery({
    queryKey: ["appointments", filters],
    queryFn: () => getAppointments(filters),
  });
}
```

Then:

```tsx
function AppointmentPage() {
  const { data, isLoading } = useAppointments(filters);

  // mostly UI
}
```

### Important senior distinction

Custom hooks are primarily for **reusing React-related behavior**, not simply because a function is getting long.

Bad reason:

> "This function is 20 lines, so let's make a hook."

Good reason:

> "This behavior involves React state/effects/query subscriptions and is reused by multiple components."

---

# 5. Don't Put Everything in Global State

This is one of the most important architecture decisions.

Bad:

```text
Redux
 ├── modal
 ├── dropdown
 ├── form input
 ├── API response
 ├── current tab
 ├── filters
 └── user preferences
```

Instead:

```text
Local state       → useState
Form state        → React Hook Form
Server state      → TanStack Query
URL state         → URL params
Shared client     → Redux/Zustand/Context
```

### Senior interview phrase

> "I avoid global state by default. I colocate state with the smallest scope that needs it and only promote it when multiple parts of the application genuinely need it."

---

# 6. Component Composition

Prefer composition over creating huge configurable components.

Instead of:

```tsx
<Modal
  showHeader
  showFooter
  showCloseButton
  showActions
  ...
/>
```

use:

```tsx
<Modal>
  <Modal.Header>
    Appointment
  </Modal.Header>

  <Modal.Body>
    ...
  </Modal.Body>

  <Modal.Footer>
    <Button>Cancel</Button>
    <Button>Confirm</Button>
  </Modal.Footer>
</Modal>
```

Why?

Because the parent controls the structure rather than the component accumulating dozens of boolean props.

### Memory trick

> **Props configure. Composition builds.**

---

# 7. Avoid Prop Drilling

Problem:

```text
App
 ↓
Dashboard
 ↓
AppointmentPage
 ↓
AppointmentList
 ↓
AppointmentCard
 ↓
Button
```

and:

```tsx
<App user={user}>
  <Dashboard user={user}>
    <AppointmentPage user={user}>
      ...
```

If `user` is needed by many distant components, consider:

```text
Context
or
shared state
```

But don't automatically use Context.

If only two components need the value, simply passing props may actually be clearer.

### Senior rule

> Prop drilling isn't inherently bad. Excessive prop drilling is a signal to reconsider ownership.

---

# 8. API Layer

Avoid calling APIs everywhere:

```tsx
fetch("/api/users")
fetch("/api/users")
fetch("/api/users")
```

Create an API boundary:

```text
Component
   ↓
useUsers()
   ↓
usersApi.getUsers()
   ↓
apiClient
   ↓
Backend
```

Example:

```ts
// usersApi.ts
export const usersApi = {
  getUsers: () =>
    apiClient.get("/users"),

  getUser: (id: string) =>
    apiClient.get(`/users/${id}`),
};
```

This gives you one place for:

* authentication
* headers
* error handling
* timeout
* serialization
* logging
* interceptors

This is especially useful in your kind of application where authentication headers and gateway tokens matter.

---

# 9. Don't Create "Utils" as a Junk Drawer

This:

```text
utils/
├── helpers.ts
├── common.ts
├── misc.ts
└── stuff.ts
```

usually becomes difficult to maintain.

Prefer meaningful ownership:

```text
appointments/
  ├── appointment.utils.ts

users/
  ├── user.utils.ts

lib/
  ├── date.ts
  └── validation.ts
```

### Senior principle

> Code should have an obvious owner.

---

# 10. Dependency Direction

A useful architecture is:

```text
UI
 ↓
Feature
 ↓
Domain/business logic
 ↓
Infrastructure/API
```

You don't want low-level infrastructure controlling your UI architecture.

For example:

```text
Button → database
```

is obviously wrong.

Better:

```text
Button
  ↓
Appointment feature
  ↓
API service
  ↓
Backend
```

# 11. What I'd Do in a Real Project

For a large appointment system:

```text
src/
├── features/
│   ├── appointments/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   ├── types.ts
│   │   └── utils.ts
│   │
│   ├── services/
│   ├── branches/
│   └── users/
│
├── components/
│   ├── Button/
│   ├── Modal/
│   └── Table/
│
├── lib/
│   ├── api-client.ts
│   ├── auth.ts
│   └── query-client.ts
│
└── routes/
```

And state:

```text
Modal open?          → local state
Form values?         → form library
Appointments?        → TanStack Query
Filters/pagination?  → URL
Global auth/session? → appropriate shared mechanism
```

That's much more scalable than putting everything into Redux or Context.

# 🧠 Senior Interview Questions

### Q1. How would you structure a large React application?

**Answer:**

> "I generally prefer feature-based architecture. Each business domain owns its components, hooks, API logic, types, and utilities, while truly reusable UI components live separately. I also separate local state, server state, URL state, and shared client state rather than putting everything into a global store."

---

### Q2. When would you create a custom hook?

> "When I have reusable React behavior involving state, effects, subscriptions, or data fetching. I don't create hooks just to move arbitrary code out of a component."

---

### Q3. How do you prevent a React codebase from becoming difficult to maintain?

Look for:

```text
✓ Feature-based organization
✓ Clear component responsibility
✓ Colocated state
✓ Server-state separation
✓ Reusable API layer
✓ Composition
✓ Small focused components
✓ Avoid unnecessary global state
✓ Clear dependency boundaries
```

---

# ⚠️ Common Senior-Level Mistakes

### ❌ "Everything should be reusable"

Over-abstraction can make simple code harder to understand.

### ❌ "Put all state in Redux"

Different state has different ownership.

### ❌ "Every component should be small"

A component can reasonably contain substantial logic if that logic belongs together.

### ❌ "Context is global state management"

Context is primarily a **dependency/value propagation mechanism**.

### ❌ "We need micro-frontends because the app is large"

Large ≠ micro-frontends.

Architecture should follow actual organizational/deployment requirements.

# 🧠 10-Second Memory

Remember:

```text
FEATURES
   ↓
Components → UI
Hooks      → behavior
API        → backend communication
Types      → contracts
Utils      → feature-specific helpers

STATE
   ↓
Local → Shared → Server → URL
```

And the senior-level principle:

> **Keep ownership close to where the behavior belongs, and only introduce shared abstractions when there is a real need.**

---

## 🎯 30-Second Interview Answer

> "For a large React application, I prefer feature-based architecture where each business domain owns its components, hooks, API logic, and types. I keep reusable UI components separate and establish clear boundaries around API communication and business logic. For state, I colocate local state, use dedicated server-state management for backend data, URL state for navigational concerns, and global state only when it's genuinely shared. The goal is to keep dependencies clear and avoid unnecessary abstractions or global state."
