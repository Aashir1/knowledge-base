# 3. Data Fetching — Senior React

This is an important topic because in real applications, a lot of React complexity comes from **API data**, not UI state.

The key mental model:

> **Fetching data is not just `fetch()` — it's caching, synchronization, loading, errors, mutations, and stale data.**

---

# 1. Basic Data Fetching

The simplest approach:

```jsx
useEffect(() => {
    fetch("/api/users")
        .then(res => res.json())
        .then(setUsers);
}, []);
```

But production applications quickly need more:

```text
API
 ↓
Loading
 ↓
Success / Error
 ↓
Cache
 ↓
Refetch
 ↓
Mutation
 ↓
Invalidate / Update cache
```

That's where a server-state library such as **TanStack Query** becomes useful.

---

# 2. Server State vs Client State

Remember from the previous topic:

```text
Client State
→ owned by the frontend

Server State
→ owned by the backend
```

Example:

```text
Client:
isModalOpen
selectedTab
theme

Server:
users
orders
appointments
products
```

Server state has unique problems:

```text
stale data
caching
refetching
deduplication
pagination
retry
network failures
mutations
synchronization
```

That's why treating API responses like ordinary `useState` can become cumbersome.

---

# 3. Query

With TanStack Query:

```jsx
const { data, isLoading, error } = useQuery({
    queryKey: ["users"],
    queryFn: fetchUsers,
});
```

Mental model:

```text
Component
    ↓
useQuery()
    ↓
Query Cache
    ↓
API
```

The important thing is:

> **The component doesn't need to own the server data lifecycle.**

---

# 4. Query Key

The query key identifies the cached data.

```js
["users"]
```

For a specific user:

```js
["users", userId]
```

For filtered users:

```js
["users", { status: "active", page: 2 }]
```

Think:

```text
Query Key
    ↓
Cache Identity
```

So:

```js
["users", 1]
```

and:

```js
["users", 2]
```

are different cached queries.

---

# 5. Caching

Suppose:

```text
User opens Products
       ↓
API request
       ↓
Products cached
```

Then they navigate away and return.

Instead of necessarily requesting everything again:

```text
Component
   ↓
Query Cache
   ↓
Existing data
```

This makes applications feel much faster.

---

# 6. Stale vs Fresh

This is an important interview concept.

Suppose the cache contains:

```text
Products fetched at 10:00
```

At 10:01, is that data invalid?

Not necessarily.

**Stale** doesn't mean:

> "The data is definitely wrong."

It means:

> "The data is considered old enough that a refetch may be appropriate."

You control this with settings such as `staleTime`.

Mental model:

```text
Fresh
 ↓
No need to refetch immediately

Stale
 ↓
May refetch when appropriate
```

---

# 7. `staleTime` vs `gcTime`

Very common interview question.

### `staleTime`

How long data is considered **fresh**.

```text
staleTime = 5 minutes
```

means:

```text
0–5 min → fresh
after 5 min → stale
```

### `gcTime`

How long **unused/inactive cached data** remains available before garbage collection.

Memory trick:

> **staleTime = freshness**
> **gcTime = cache lifetime**

Don't confuse them.

---

# 8. Loading vs Fetching

Another useful distinction.

Suppose the first request happens:

```text
No data
   ↓
Loading
   ↓
Data
```

Later:

```text
Existing data
   ↓
Background refetch
   ↓
Updated data
```

The user may still see the existing data while a request happens in the background.

This gives a much better UX than:

```text
Every request
   ↓
Blank screen
   ↓
Spinner
```

---

# 9. Mutations

Queries generally **read** data.

Mutations change server data:

```text
POST
PUT
PATCH
DELETE
```

Example:

```jsx
const mutation = useMutation({
    mutationFn: createAppointment,
});
```

Then:

```js
mutation.mutate(appointment);
```

Mental model:

```text
Query
→ Read server data

Mutation
→ Change server data
```

---

# 10. Cache Invalidation

Suppose:

```text
GET /appointments
```

returns:

```text
Appointment A
Appointment B
```

You create:

```text
Appointment C
```

Your existing cache may still contain:

```text
A
B
```

So after the mutation, you can invalidate the relevant query.

```js
queryClient.invalidateQueries({
    queryKey: ["appointments"],
});
```

Flow:

```text
Create appointment
       ↓
Mutation succeeds
       ↓
Invalidate appointments
       ↓
Refetch
       ↓
A B C
```

### Senior concept

> **Mutations must keep the client cache consistent with the server.**

---

# 11. Optimistic Updates

Instead of waiting for:

```text
API
 ↓
Success
 ↓
Update UI
```

you can:

```text
User action
 ↓
Update cache immediately
 ↓
API request
 ↓
Success → keep it
Failure → rollback
```

Example:

```text
Like button

Before:
♡ 10

Click:
♥ 11

API fails:
♡ 10
```

This makes UI feel extremely responsive.

But:

> **Optimistic updates require rollback/error handling.**

Don't use them blindly.

---

# 12. Pagination

Suppose there are:

```text
100,000 appointments
```

Don't fetch everything.

Use:

```text
GET /appointments?page=1&limit=20
```

Then:

```text
Page 1
Page 2
Page 3
...
```

There are different strategies:

### Offset pagination

```text
?page=2&limit=20
```

Simple, but can become problematic with frequently changing datasets.

### Cursor pagination

```text
?cursor=eyJpZCI6...
```

The server returns a cursor for the next page.

Better suited to large/changing datasets in many scenarios.

---

# 13. Search / Filtering

Consider:

```text
/cases?status=open&priority=high&page=2
```

These parameters should usually be part of your query identity.

Conceptually:

```js
["cases", {
    status: "open",
    priority: "high",
    page: 2
}]
```

Now each combination can have its own cache.

---

# 14. Dependent Queries

Sometimes query B depends on query A.

Example:

```text
Get user
  ↓
Get user's appointments
```

You shouldn't request appointments before you know the user.

Mental model:

```text
User query
   ↓
user.id
   ↓
Appointments query enabled
```

This is called a **dependent query**.

---

# 15. Parallel Queries

Sometimes requests are independent.

```text
Dashboard
 ├── Users
 ├── Revenue
 ├── Orders
 └── Notifications
```

Don't unnecessarily make:

```text
Users
 ↓
Revenue
 ↓
Orders
 ↓
Notifications
```

Instead:

```text
      ┌→ Users
API ──┼→ Revenue
      ├→ Orders
      └→ Notifications
```

Parallel fetching reduces total waiting time.

---

# 16. Request Deduplication

Imagine two components both request:

```js
["users"]
```

A good server-state library can recognize that they're asking for the same query and avoid unnecessary duplicate network requests.

This is another benefit over manually sprinkling `fetch()` across components.

---

# 17. Error & Retry

Network failures happen.

You need to distinguish:

```text
4xx
→ Usually application/user problem

5xx
→ Server problem

Network error
→ Connectivity problem
```

Don't blindly retry every error.

For example:

```text
401 Unauthorized
→ retrying won't magically authenticate the user

500 Server Error
→ retry may make sense

Network timeout
→ retry may make sense
```

Senior-level thinking:

> **Retry strategy should depend on the failure type.**

---

A production React application might look like:

                 React

```text

```

# Senior Interview Questions

### 1. Why use TanStack Query instead of `useEffect + useState`?

> `useEffect + useState` works for simple cases, but as server-state requirements grow, we need caching, stale-data handling, refetching, retries, deduplication, pagination, and mutation management. A server-state library provides these capabilities systematically.

---

### 2. What is stale data?

> Data that the caching system considers old enough that it may need to be refetched. Stale doesn't necessarily mean incorrect.

---

### 3. `staleTime` vs `gcTime`?

> `staleTime` controls how long data is considered fresh. `gcTime` controls how long inactive cached data can remain before garbage collection.

---

### 4. Query vs Mutation?

> Queries primarily retrieve server data, while mutations perform operations that change server-side data.

---

### 5. What happens after a successful mutation?

A good answer:

> I need to make sure any affected cached queries remain consistent. Depending on the operation, I might invalidate the relevant queries, directly update the cache, or perform an optimistic update with rollback.

---

### 6. When would you use optimistic updates?

> When the expected result is highly predictable and immediate UI feedback significantly improves UX, while having a reliable rollback strategy if the server rejects the operation.

---

### 7. How would you handle 100,000 records?

> I wouldn't fetch them all. I'd use server-side pagination, filtering and sorting, preferably cursor pagination where appropriate, and fetch only the data required by the UI.

---

### 8. How would you avoid duplicate API requests?

> Use a centralized server-state/cache layer with stable query keys and request deduplication rather than having independent components manually fetch the same resource.

# Senior Scenario

Imagine your appointment system:

```text
Appointment Dashboard

├── Available services
├── Branches
├── Available slots
├── User appointments
└── Appointment details
```

I'd expect you to reason like this:

```text
Services
    → server state

Branches
    → server state

Available slots
    → server state
    → probably short staleTime

User appointments
    → server state

Selected date
    → local / URL state

Modal open
    → local state

Create appointment
    → mutation

After successful creation
    → invalidate/update appointments

Large appointment list
    → server pagination
```

Notice the pattern:

> **Don't ask "Which React library should I use?" first. Ask "What kind of state/data is this?"**
