# 2. State Management — Senior React

The key thing at senior level is **not knowing Redux/Zustand APIs**. It's knowing:

> **What state should live where, and why?**

---

## 1. The State Categories

A useful mental model is to divide state into 4 types:

```text
                    Application State
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
   Local UI State    Shared Client      Server State
                         State
        │                 │                 │
    useState          Context/Redux      React Query
```

And one more:

```text
URL State
```

### Local UI state

State used by one component or a small local tree.

```js
const [isOpen, setIsOpen] = useState(false);
```

Examples:

* Modal open/closed
* Input value
* Selected tab
* Dropdown state

**Default choice:** `useState`

---

### Shared client state

State needed by many unrelated components.

Examples:

* Current user
* Theme
* Shopping cart
* Complex multi-step workflow
* Global UI state

Possible tools:

```text
Context
Redux
Zustand
```

---

### Server state

Data that belongs to your backend.

Examples:

```text
users
products
orders
appointments
notifications
```

This is fundamentally different from local UI state because it has:

* caching
* loading
* errors
* stale data
* refetching
* synchronization
* pagination
* mutations

A tool like **TanStack Query** is often more appropriate than putting all of this into Redux.

---

### URL state

Don't forget the URL.

Example:

```text
/products?category=phones&page=2&sort=price
```

This is state too.

Use URL state for things that should be:

* shareable
* bookmarkable
* browser-navigation friendly

---

# 2. The Most Important Senior Question

### "Where should this state live?"

Use this decision process:

```text
Does only one component need it?
        │
       YES
        ↓
     useState

        NO
        ↓
Do several components need it?
        │
       YES
        ↓
Can they share it through composition/Context?
        │
      YES → Context
        │
       NO
        ↓
Client state manager
Redux / Zustand

        ↓
Is the data owned by the backend?
        │
       YES
        ↓
Server-state solution
TanStack Query
```

The important principle:

> **Don't put everything into global state.**

---

# 3. Context vs Redux

This is a very common interview question.

### Context

Good for relatively stable cross-cutting values:

```jsx
<ThemeContext.Provider value={theme}>
```

Examples:

* Theme
* Locale
* Current authenticated user
* Configuration

Context primarily solves:

> **How do I make a value available to many components without prop drilling?**

It is **not automatically a complete state-management solution**.

---

### Redux

Redux is useful when application state becomes:

* large
* shared
* complex
* frequently updated
* difficult to reason about locally

Redux gives you a predictable state model:

```text
Component
   ↓
dispatch(action)
   ↓
Reducer
   ↓
Store
   ↓
Component
```

Example:

```js
dispatch({
    type: "cart/itemAdded",
    payload: product
});
```

---

# 4. Why Not Put Everything in Context?

Suppose:

```jsx
<AppContext.Provider value={{
    user,
    cart,
    notifications,
    searchResults,
    theme
}}>
```

Now many components consume the same context.

When the provider value changes, consumers can be affected even when they only care about one part of the value.

You can end up with:

```text
Context changes
      ↓
Many consumers update
      ↓
Potential unnecessary work
```

Context isn't inherently slow, but using one giant context for frequently changing application state is usually poor architecture.

---

# 5. Redux vs Zustand

You don't need to memorize every API.

Think conceptually:

### Redux

```text
Centralized store
      ↓
Actions
      ↓
Reducers
      ↓
Predictable state transitions
```

Strengths:

* predictable
* strong conventions
* middleware
* devtools
* large ecosystem
* good for complex applications

Tradeoff:

* more structure/boilerplate

---

### Zustand

Think:

```text
Small store
     ↓
Components subscribe to what they need
```

Example:

```js
const useCartStore = create((set) => ({
    items: [],
    addItem: (item) =>
        set(state => ({
            items: [...state.items, item]
        }))
}));
```

Strength:

> Simple global client state with relatively little ceremony.

---

# 6. Client State vs Server State

This distinction is **very important for senior interviews**.

Suppose you have:

```js
const [users, setUsers] = useState([]);
```

and you're fetching users from an API.

You now have to deal with:

```text
loading
error
retry
cache
stale data
refetch
pagination
mutation
deduplication
```

That's not really just "React state."

It's **server state**.

A server-state library can manage this:

```text
Component
    ↓
useQuery()
    ↓
Cache
    ↓
API
```

For example:

```js
const { data, isLoading, error } = useQuery({
    queryKey: ["users"],
    queryFn: fetchUsers
});
```

---

# 7. Why Query Keys Matter

Example:

```js
["users"]
```

versus:

```js
["users", { page: 2 }]
```

The query key identifies the cached data.

Think:

```text
Query Key
    ↓
Cache Identity
```

So:

```text
["users", 1]
["users", 2]
```

can represent different cached pages.

---

# 8. Optimistic Updates

Very common senior interview topic.

Suppose a user likes a post.

Normal approach:

```text
Click Like
   ↓
API request
   ↓
Success
   ↓
Update UI
```

This can feel slow.

Optimistic update:

```text
Click Like
   ↓
Immediately update UI
   ↓
API request
   ↓
Success → keep change
   ↓
Failure → rollback
```

The key idea:

> **Assume success temporarily, but have a rollback strategy.**

---

# 9. State Colocation

One of the most useful React architecture principles.

Bad:

```text
Global Store
 ├── modal
 ├── inputValue
 ├── selectedTab
 ├── dropdown
 ├── tooltip
 └── everything else
```

Better:

```text
Component
 └── local UI state

Feature
 └── feature state

Global Store
 └── genuinely global state
```

This is called **state colocation**.

> Keep state as close as possible to where it is used.

---

# 10. Derived State

Avoid storing something you can calculate.

Bad:

```js
const [firstName, setFirstName] = useState("Aashir");
const [lastName, setLastName] = useState("Khan");
const [fullName, setFullName] = useState("Aashir Khan");
```

`fullName` is derived from other state.

Better:

```js
const fullName = `${firstName} ${lastName}`;
```

Memory trick:

> **If you can calculate it, don't store it.**

This avoids synchronization bugs.

# Senior Interview Questions

### 1. How do you decide whether state should be local or global?

> Start local. Move it upward or into shared state only when multiple parts of the application genuinely need it.

---

### 2. Context vs Redux?

> Context is primarily a mechanism for sharing values through the component tree. Redux is a dedicated state-management architecture with centralized state, actions, reducers, middleware, and tooling. Context is often enough for relatively simple cross-cutting state, while Redux becomes useful when shared client state and its transitions become complex.

---

### 3. Should API data be stored in Redux?

> It can be, but I generally separate server state from client state. A server-state library such as TanStack Query provides caching, stale-time management, refetching, mutations, and synchronization that you'd otherwise have to build yourself.

---

### 4. What is state colocation?

> Keeping state as close as possible to the components that use it instead of putting everything into global state.

---

### 5. What is derived state?

> State that can be calculated from existing state or props. I generally avoid storing it separately because that can create synchronization bugs.

---

### 6. What is optimistic UI?

> Updating the UI immediately assuming the server operation will succeed, then confirming the change or rolling it back if the request fails.

---

### 7. When would you use URL state?

> When state should be shareable, bookmarkable, or preserved through browser navigation, such as filters, pagination, search queries, and sorting.

---

### 8. Why can a large Context become problematic?

> A frequently changing context can cause many consumers to re-evaluate when its value changes. Splitting contexts and keeping state local can reduce unnecessary updates and make the architecture easier to reason about.

# Senior Scenario

Imagine you're building your **RER appointment application**:

```text
Appointment Form
├── selected service
├── selected branch
├── date
├── time
├── applicant information
├── uploaded documents
└── appointment status
```

Don't immediately create:

```text
Redux
 └── EVERYTHING
```

Instead think:

```text
Local UI
 ├── modal open
 └── dropdown state

Form state
 └── React Hook Form

Server state
 ├── available services
 ├── branches
 ├── available slots
 └── appointment

URL state
 └── filters / navigation params

Global client state
 └── genuinely shared application state
```

That's the **senior-level way of thinking about state management**.

# 🧠 30-Second Memory

Remember **L-S-U**:

```text
L = Local
S = Shared client
U = URL / Server
```

More practically:

```text
UI state       → useState
Shared state   → Context / Redux / Zustand
Server data    → TanStack Query
URL state      → URL params/search params
Derived data   → calculate it
```

And the golden rule:

> **Start local → colocate → share only when necessary → don't treat server data like ordinary client state.**
