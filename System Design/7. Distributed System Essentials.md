# Day 6 — Distributed Systems Essentials

This is an important day because we're going to connect many things you've already learned.

The goal isn't to learn complicated distributed-systems theory. It's to answer questions like:

> "What happens when two servers/processes change the same data at the same time?"

> "What happens when one service succeeds and another fails?"

> "How do we keep multiple servers consistent?"

---

## 1. First: What is a Distributed System?

You've already been designing distributed systems without necessarily calling them that.

For example:

```text
                Load Balancer
                 /    |    \
                ↓     ↓     ↓
              API1   API2   API3
                \     |     /
                     ↓
                  Database
```

We have multiple machines working together.

That's a distributed system.

The problem is that **these machines don't share memory and can fail independently.**

For example:

```text
API1 → Database ✅

API2 → Database ❌

API3 → Database ✅
```

Or:

```text
Service A → Service B
              ↓
             💥
```

This creates problems that don't exist in a single-process application.

---

# 2. The First Important Problem: Race Conditions

Suppose a bank account has:

```text
Balance = $100
```

Two requests arrive simultaneously.

```text
Request A: Withdraw $80
Request B: Withdraw $80
```

Both servers read:

```text
Balance = $100
```

Then both think:

```text
100 - 80 = 20
```

So:

```text
API 1 → $20
API 2 → $20
```

But the user withdrew:

```text
$160
```

from an account containing:

```text
$100
```

That's a **race condition**.

---

# 3. Why Does This Happen?

Because the operation wasn't atomic.

We effectively did:

```text
READ balance
      ↓
calculate
      ↓
WRITE balance
```

Two processes can interleave those operations.

```text
API 1              API 2

READ = $100
                   READ = $100

calculate $20
                   calculate $20

WRITE $20
                   WRITE $20
```

The second write overwrites the first.

---

# 4. Database Transactions

One solution is a database transaction.

Conceptually:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 80
WHERE id = 123
  AND balance >= 80;

COMMIT;
```

The database can ensure that concurrent operations don't incorrectly modify the same row.

This is why we don't immediately reach for Redis or distributed locks.

### Important rule

> **If the problem can be safely solved inside the database transaction, prefer the database.**

Don't add distributed complexity unnecessarily.

---

# 5. Distributed Locks

But sometimes the operation involves something outside the database.

For example:

```text
Worker 1 ─┐
          ├──► External API
Worker 2 ─┘
```

Maybe only one worker should perform an operation at a time.

We might use a distributed lock:

```text
Worker 1
   ↓
Acquire lock
   ↓
Perform operation
   ↓
Release lock
```

While:

```text
Worker 2
   ↓
Try lock
   ↓
LOCKED
   ↓
Wait / retry
```

Redis is sometimes used to implement distributed locks.

But again:

> **Don't use a distributed lock unless you actually have a coordination problem that requires one.**

---

# 6. The Bigger Problem: Multiple Services

Now imagine an e-commerce system.

A customer places an order:

```text
Client
  ↓
Order Service
  ↓
Payment Service
  ↓
Inventory Service
```

Suppose:

```text
Order created       ✅
Payment successful  ✅
Inventory update    ❌
```

Now what?

We have:

```text
Order = CREATED
Payment = PAID
Inventory = NOT RESERVED
```

That's a distributed transaction problem.

---

# 7. Why Can't We Just Use One Transaction?

Because these might be completely separate services/databases:

```text
Order DB
Payment DB
Inventory DB
```

You can't simply do:

```text
BEGIN TRANSACTION

Order DB
Payment DB
Inventory DB

COMMIT
```

as easily as one database transaction.

Now we need distributed-system patterns.

---

# 8. Eventual Consistency

Here's an important concept.

Sometimes we don't need every service to immediately have exactly the same state.

Example:

```text
Order Service
     ↓
Order = CREATED
     ↓
Event
     ↓
Payment Service
     ↓
Payment = PAID
```

There may be a small delay:

```text
t=0
Order = CREATED
Payment = UNKNOWN

t=1 sec
Payment = PAID
```

The system eventually becomes consistent.

That's:

### Eventual consistency

The system may temporarily have different views of the data, but they eventually converge.

---

# 9. Strong vs Eventual Consistency

Think about a social-media like count.

```text
User clicks Like
```

Do we really need every server to immediately show:

```text
1,000,001 likes
```

Probably not.

A delay of a second may be acceptable.

That's a good candidate for eventual consistency.

But consider:

```text
Bank balance
```

You generally don't want:

```text
Server A → $100
Server B → $20
```

and allow another withdrawal based on stale information.

That's where stronger consistency matters.

---

# 10. The Interview Question

Interviewers may ask:

> "Would you use strong or eventual consistency?"

Don't answer automatically.

Instead ask:

> **"What consistency does the business requirement actually need?"**

For example:

| Data                | Typical requirement                       |
| ------------------- | ----------------------------------------- |
| Bank balance        | Stronger consistency                      |
| Inventory count     | Strong consistency / carefully controlled |
| Social likes        | Eventual consistency often acceptable     |
| Analytics           | Eventual consistency                      |
| Notification status | Often eventual consistency                |
| Search index        | Usually eventual consistency              |

The exact choice depends on the system.

---

# 11. CAP Theorem

Now we can introduce CAP.

CAP says that in the presence of a **network partition**, a distributed system has to choose between:

```text
Consistency
Availability
```

You may see:

```text
C
A
P
```

### Consistency

Every read gets the appropriate latest value according to the system's consistency model.

### Availability

Every request receives a response from a non-failing node.

### Partition tolerance

The system continues operating despite communication failures between nodes.

---

# 12. Why Is P Basically Assumed?

Because networks can fail.

Imagine:

```text
Server A
   X
Server B
```

They can't communicate.

That's a partition.

You have to decide:

### Option A

Stop accepting some operations:

```text
Consistency ↑
Availability ↓
```

### Option B

Continue serving requests:

```text
Availability ↑
Consistency ↓
```

That's the practical CAP trade-off.

---

# 13. Don't Memorize "Pick Two"

This is a common interview mistake.

People say:

> "CAP means choose two out of three."

That's an oversimplification.

The useful interview understanding is:

> **When a network partition happens, you generally have to trade consistency against availability.**

That's what I want you to remember.

---

# 14. Another Important Concept: Idempotency

You already learned this on Day 4.

Now see how it fits distributed systems.

Suppose:

```text
POST /payment
```

Client sends:

```text
payment_id = 123
```

Request reaches server.

Payment succeeds.

But response is lost:

```text
Server ──► Payment Provider
             ↓
           SUCCESS
             X
          response lost
```

Client doesn't know whether it succeeded.

So it retries:

```text
POST /payment
payment_id = 123
```

Without idempotency:

```text
Charge #1 = $100
Charge #2 = $100
```

With idempotency:

```text
payment_id = 123

Already processed?
YES

Return existing result.
```

This is why **idempotency is one of the most important Senior-level concepts**.

---

# 15. Outbox Pattern

Now one more important pattern.

Imagine:

```text
Order Service
     │
     ├── Save order to DB
     │
     └── Publish event
```

What if:

```text
Save DB → SUCCESS
Publish event → FAILURE
```

Now:

```text
Order exists
BUT
Payment service doesn't know
```

We can use an **outbox**.

Instead of:

```text
DB
 +
Message Queue
```

separately, we write the event into the same database transaction:

```text
BEGIN

Orders
   ↓
save order

Outbox
   ↓
save "OrderCreated" event

COMMIT
```

Then a background process publishes outbox events:

```text
Database
   ↓
Outbox
   ↓
Publisher
   ↓
Queue
   ↓
Payment Service
```

If the publisher crashes:

```text
Outbox event remains in DB
```

So it can try again.

This is a very useful pattern to recognize in Senior interviews.

---

# 16. Our Mental Model for Day 6

You should now start seeing distributed systems as a collection of problems:

```text
Distributed Systems
        │
        ├── Concurrent operations
        │      ↓
        │   Race conditions
        │
        ├── Multiple databases/services
        │      ↓
        │   Consistency
        │
        ├── Network failures
        │      ↓
        │   CAP trade-offs
        │
        ├── Retries
        │      ↓
        │   Idempotency
        │
        └── DB + messaging
               ↓
            Outbox
```

# Day 6 — Interview Notes

### Race condition

> Multiple operations access/change shared state concurrently and produce an incorrect result.

### Transaction

> Atomic unit of database work.

### Strong consistency

> Reads reflect the latest committed state according to the system's consistency guarantees.

### Eventual consistency

> Updates propagate asynchronously and replicas/services eventually converge.

### CAP

> During a network partition, distributed systems must trade off consistency and availability.

### Distributed lock

> Coordinates access to a shared resource across multiple processes/servers.

### Idempotency

> Repeating the same operation doesn't create additional unintended effects.

### Outbox

> Store the database change and the event in the same DB transaction, then publish the event asynchronously.

# One Very Important Senior Interview Habit

When you see a system-design problem, **don't immediately start adding components**.

Instead ask:

```text
What can go wrong?
       ↓
What requirement do we have?
       ↓
What is the simplest solution?
       ↓
Where is the bottleneck/failure?
       ↓
Only then add complexity.
```

You've already been doing this with:

```text
Queue → because provider is slow
Redis → because shared state/rate limiting requires it
Read replica → because reads become a DB bottleneck
CDN → only when static/global content needs edge delivery
```

That's exactly the thinking we're trying to develop.
