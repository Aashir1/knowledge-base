# Design a Notification System

### Quick Revision 🧠

> A system that reliably delivers a message to a user across channels (push/SMS/email) by decoupling "accept the request" from "actually send it."

```text
Client → API (fast accept) → Priority Queue → Worker (slow send) → Provider → User
                                                    ↓
                                          DB: status + idempotency key
```

→ Never call the provider synchronously from the API — that couples your API's latency/availability to theirs.
→ Queue = at-least-once delivery. Idempotency (dedupe by `notification_id`) is what actually stops duplicates.
→ OTP/security alerts need their own priority lane so a marketing blast can't delay them.
→ A user has multiple devices — fan out to all of them; re-check preferences right before sending, not just at enqueue.

**Say this in an interview:** "I'd decouple accepting the request from delivering it with a queue, use worker pools per priority tier, track status by ID for idempotent retries, and fail over to a backup provider on outage."

## 1. Requirements & Estimation

```text
Functional:   push/SMS/email → triggered by services + scheduled jobs
              → user preferences (category-level opt-out, never for security alerts)
              → multiple devices per user

Non-functional: at-least-once delivery, no duplicates, provider outage ≠ system outage
              → OTP needs sub-second latency, marketing is best-effort
```

```text
Assume: 100M DAU × 2 notifications/day ÷ 86,400s ≈ 2,315/sec average
average × 5x peak factor ≈ 11,500/sec peak
peak × 0.2s/send ≈ 2,300 concurrent workers needed
```
*(numbers are illustrative — the reusable part is the method: users → rate → resource count)*

## 2. High-Level Design

```text
Trigger service → API → Priority Queues (HIGH|MEDIUM|LOW) → Worker Pool
                                                                  │
                                            ┌─────────────────────┼───────────────┐
                                            ▼                     ▼               │
                                   Preference Check       Provider Adapter        │
                                                          (primary → fallback)     │
                                                                  ▼               │
                                                              User's device(s)◄───┘
                                                                  │
                                                                  ▼
                                                    Notification DB (status + idempotency)
```

API's only job: validate, enqueue, return "accepted." Everything slow happens off the request path.

## 3. Core Reliability Model — Queue, ACK, Idempotency

This is the part worth understanding deeply — it's the concept most likely to get grilled.

### Naive: call the provider directly

```text
Client → API → SMS Provider → User
```
At 11,500 req/sec, API servers sit blocked waiting 1-3s per provider response — the API's own throughput becomes capped by a third party.

### Fix: put a queue in between

```text
Client → API → Queue → Worker → SMS Provider → User
```
API replies "accepted" instantly; a worker pool handles the slow part separately — like a restaurant queue, any free waiter takes the next order.

### The failure this introduces

```text
Worker sends SMS #123 → provider returns SUCCESS → user receives it
    ↓
Worker CRASHES before ACKing the queue
    ↓
Queue assumes #123 failed → gives it to Worker 2
    ↓
User receives the SAME SMS again
```
No ACK before a crash means the queue *correctly* retries — that's why the queue alone can't prevent duplicates.

### The actual fix: idempotency

```text
notification_id | status
123              | SENT
```
Worker checks "is #123 already SENT?" before sending — if yes, skip and ACK. Queue = at-least-once. Idempotency = effectively-once for the user.

## 4. The Missing Pieces — Pattern Cards

Each of these is a real gap a naive design has. Shallower than the reliability model above — the pattern and the one-line "why" is what matters, not a full failure narrative each.

**Priority Tiers** — one shared queue lets a 1M-message campaign bury a password-reset OTP behind it.
```text
HIGH → OTP, security     (own queue, own worker pool)
MED  → transactional
LOW  → marketing         (batched, rate-limited)
```
→ Separate *worker pools*, not just a priority field — shared workers still get consumed by the low-priority burst.

**Provider Failover** — retrying a dead provider forever backs up the whole queue behind it.
```text
Worker → Primary Provider ──(N failures)──► Circuit breaker OPENS ──► Secondary Provider
```
→ Stop hammering a provider that's down; degrade to a fallback instead of stalling everything.

**Preferences / Opt-Out** — checking only at enqueue time can be stale by send time.
```text
Enqueued (preference OK) → user opts out 5s later → sent 2min later anyway ❌
```
→ Re-check preferences right before send, not only at enqueue.

**Multi-Device Fan-Out** — treating each device as its own notification fragments status tracking.
```text
Device Registry: userId → [token A, token B, token C]
One event → fan out to ALL active tokens in parallel, status stays keyed to the ONE event
```
→ Prune invalid/expired tokens when the provider reports them, or the registry rots.

**Permanent Failures** — retrying forever wastes worker capacity on things that will never succeed.
```text
Retry with backoff, up to N attempts → still failing → Dead Letter Queue
```
→ DLQ stops one bad message from consuming capacity forever, and makes failures inspectable.

---

## 5. Tradeoffs

```text
At-least-once + idempotency  →  exactly-once is expensive; rarely worth it
Per-tier queues               →  more infra, but the only real guarantee against starvation
Checking preferences twice    →  one extra read, avoids a just-opted-out send
```

## 6. Senior Interview Questions

**Q1. Why put a queue between the API and the provider?**
The provider's 1-3s response time would cap the API's own throughput otherwise. The queue lets the API accept instantly.

**Q2. How do you prevent duplicate notifications?**
The queue only guarantees at-least-once — duplicates come from retries after a crash before ACK. Idempotency (status check by `notification_id`) blocks the actual duplicate send.

**Q3. How do you stop a campaign from delaying OTP delivery?**
Separate queues *and* worker pools per tier — a shared pool still lets a low-priority burst consume all the capacity, priority field or not.

**Follow-up:** Why isn't a priority field on one queue enough? → Workers pull from one pool of capacity regardless of pop order; a big low-priority burst can occupy every worker at once.

**Q4. What happens if the primary provider goes down?**
Circuit breaker detects repeated failures, opens, routes new sends to a secondary provider until the primary recovers.

**Q5. How do you estimate the worker count?**
`workers ≈ peak QPS × avg processing time`. ~11,500/sec × 0.2s ≈ 2,300 — a starting point to validate under load, not a final number.

**Q6. A user opts out 30 seconds before a queued notification would send — what happens?**
Sends anyway if preferences were only checked at enqueue. Fix: re-check right before send.

**Q7. How do you avoid 5 copies of one event for a user with 5 devices?**
A device registry maps user → active tokens; one job fans out to all of them, status stays keyed to the original event, not per-device.

**Q8. What do you do with a notification that keeps failing?**
Retry with backoff up to a limit, then Dead Letter Queue — stops it from consuming worker capacity forever and keeps failures inspectable.
