# Day 4 — Notification System Deep Dive

## 1. The Most Important Problem: At-Least-Once Delivery

Our queue generally gives us **at-least-once delivery**.

That means:

> A message will be delivered one or more times.

It does **not** mean exactly once.

Consider:

```text
Queue
  │
  ▼
Worker
  │
  ├── Send SMS ──────────► Provider
  │                          │
  │                       SUCCESS
  │
  └── Mark processed
```

Looks fine.

But what if:

```text
Worker
  │
  ├── Send SMS ──────────► Provider
  │                          │
  │                       SUCCESS
  │
  X CRASH
```

The worker never acknowledges the message.

The queue thinks:

> "Nobody successfully processed this."

So it redelivers:

```text
Queue
  │
  ▼
Worker 2
  │
  └── Send SMS ──────────► Provider
```

Now the user receives **two SMS messages**.

This is one of the most important distributed-systems interview problems.

---

# 2. Idempotency

The solution is **idempotency**.

An operation is idempotent when performing it multiple times produces the same intended result as performing it once.

For notifications, we can create an idempotency key:

```text
notification_id = "notif_12345"
```

Database:

```text
notifications

id          user_id     type     status
------------------------------------------
notif_123   user_1      SMS      PROCESSING
```

Worker receives:

```text
{
  "notificationId": "notif_123",
  "type": "SMS",
  "recipient": "+1...",
  "message": "Your OTP is..."
}
```

Before processing:

```text
Does notif_123 already exist as successfully processed?
```

If:

```text
status = SENT
```

Then:

```text
skip
ACK message
```

Otherwise process it.

---

# 3. But There Is a Subtle Problem

You might propose:

```text
check DB
↓
send SMS
↓
update DB = SENT
```

But there's still a race:

```text
Worker
  │
  ├── check → NOT SENT
  │
  ├── send SMS → SUCCESS
  │
  X crash
  │
  └── never updates DB
```

Next worker:

```text
check DB → NOT SENT
send SMS → SUCCESS
```

Duplicate again.

### Important realization

You **cannot reliably achieve exactly-once side effects** across your database and an external provider using a simple transaction.

This is why we usually design for:

> **At-least-once processing + idempotent side effects.**

---

# 4. How Can We Make the Provider Call Idempotent?

Best case:

The provider itself supports an idempotency key.

```text
POST /send

Idempotency-Key: notif_123
```

First request:

```text
notif_123 → SMS sent
```

Retry:

```text
notif_123 → already processed
```

Provider returns the previous result rather than sending another SMS.

This is the cleanest solution.

But what if the provider **doesn't support idempotency**?

Then we have a harder distributed-systems problem.

We can maintain our own state:

```text
notification
     │
     ├── PENDING
     ├── PROCESSING
     ├── SENT
     └── FAILED
```

But there is still a tiny unavoidable uncertainty window:

```text
Provider SUCCESS
       ↓
Network response lost
       ↓
Worker doesn't know whether it succeeded
```

Worker has two choices:

```text
Retry
```

Potential duplicate.

or:

```text
Don't retry
```

Potential lost notification.

### Senior-level answer

Say:

> "Exactly-once delivery to an external provider isn't something I'd assume. I'd use at-least-once queue semantics and make the downstream operation idempotent where the provider supports an idempotency key. Otherwise, there's an unavoidable ambiguity window between the external side effect and our state update, so we'd explicitly accept the duplicate-vs-loss trade-off."

That's a **very strong interview answer**.

---

# 5. Queue Acknowledgement

Now let's understand ACK.

Worker receives:

```text
Queue
 ↓
Worker
```

The queue usually doesn't immediately remove the message.

Instead:

```text
Message
 ↓
Worker receives
 ↓
Message becomes invisible / leased
 ↓
Worker processes
 ↓
ACK
 ↓
Queue removes message
```

If worker crashes before ACK:

```text
Worker crashes
       ↓
No ACK
       ↓
Visibility timeout expires
       ↓
Queue makes message available again
       ↓
Another worker processes it
```

This gives us:

**At-least-once delivery.**

---

# 6. Visibility Timeout

Imagine processing takes up to 30 seconds.

We configure:

```text
visibility timeout = 60 sec
```

Worker:

```text
t=0     receive
t=10    processing
t=20    provider call
t=25    success
t=26    ACK
```

Fine.

But if:

```text
t=0     receive
t=65    still processing
```

The message may already become visible again.

Now:

```text
Worker 1
   │
   └──── processing ───────────────┐
                                    │
Queue ─────── redeliver ─────► Worker 2
```

Two workers process the same message.

Again:

**Idempotency is essential.**

---

# 7. Retry Strategy

Suppose the provider returns:

```text
HTTP 503
```

Don't immediately retry 10 times.

Bad:

```text
request
 ↓
failure
 ↓
retry
 ↓
failure
 ↓
retry
 ↓
failure
```

Thousands of workers can create a retry storm.

Instead:

```text
Attempt 1
   ↓
1 sec
   ↓
Attempt 2
   ↓
2 sec
   ↓
Attempt 3
   ↓
4 sec
   ↓
Attempt 4
   ↓
8 sec
```

This is:

### Exponential backoff

Usually add **jitter**:

```text
delay = exponential_backoff + random_jitter
```

Why?

Imagine 10,000 messages fail simultaneously.

Without jitter:

```text
all retry at 10:00:10
```

With jitter:

```text
10:00:08
10:00:09
10:00:11
10:00:12
...
```

This spreads the load.

---

# 8. Not Every Failure Should Retry

This is important.

### Retryable

```text
503 Service Unavailable
502 Bad Gateway
429 Too Many Requests
network timeout
connection failure
```

### Usually NOT retryable

```text
400 Bad Request
invalid phone number
invalid email
malformed request
invalid authentication credentials
```

If the email address is invalid:

```text
retry 10 times
```

won't magically make it valid.

So:

```text
Provider response
       │
       ├── retryable → retry
       │
       └── permanent → failed/DLQ
```

---

# 9. Dead Letter Queue

Suppose:

```text
max retries = 5
```

After:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
Attempt 4 ❌
Attempt 5 ❌
```

Don't keep retrying forever.

Move it:

```text
Main Queue
     │
     ▼
 Worker
     │
     ▼
 Retry
     │
     ▼
 Retry
     │
     ▼
 Retry limit
     │
     ▼
    DLQ
```

DLQ allows engineers to investigate:

```text
Why did this notification fail?
```

And potentially replay it after fixing the problem.

---

# 10. Multiple Notification Types

Our original design has:

```text
Queue
 ↓
Workers
 ↓
Email
SMS
Push
```

This works initially.

But suppose SMS suddenly has a provider outage.

If everything shares one queue:

```text
Email ─┐
SMS ───┼──► Queue
Push ──┘
```

SMS retries can consume worker capacity and affect email/push.

A better architecture at larger scale:

```text
                    ┌── Email Queue ──► Email Workers
                    │
API ─► Notification ├── SMS Queue ────► SMS Workers
                    │
                    └── Push Queue ───► Push Workers
```

Now SMS failure doesn't necessarily impact email.

### But don't add this automatically.

At smaller scale:

```text
one queue + worker routing
```

may be completely sufficient.

Introduce separate queues when you need:

* independent scaling
* independent retry policies
* isolation between workloads
* provider-specific rate limits
* different priority requirements

This is exactly the type of **trade-off** interviewers want to hear.

---

# 11. Provider Rate Limits

Suppose our SMS provider allows:

```text
1,000 requests/sec
```

But our system receives:

```text
10,000 notifications/sec
```

If we simply scale workers:

```text
100 workers
```

we could overwhelm the provider.

So worker scaling alone isn't enough.

We need:

```text
Queue
 ↓
Workers
 ↓
Rate Limiter
 ↓
Provider
```

For example:

```text
Provider limit = 1,000/sec

Worker fleet
    ↓
Distributed rate limiter
    ↓
max 1,000 requests/sec
    ↓
Provider
```

Redis can be useful here for distributed rate limiting.

But notice the principle:

> **Redis isn't there because "system design requires Redis."**

It's there because we have a specific distributed rate-limiting problem.

---

# 12. Queue Ordering

Suppose a user performs:

```text
1. Password reset
2. Account activated
3. Welcome email
```

Do we care about order?

Maybe.

For some systems:

```text
A → B → C
```

must be processed in order.

For others:

```text
A
B
C
```

can be processed independently.

Ordering usually reduces parallelism.

You may need:

```text
partition key = user_id
```

Then:

```text
user_123
   ↓
Partition 7
   ↓
A → B → C
```

while:

```text
user_456
   ↓
Partition 12
```

can process independently.

### Interview principle

Ask:

> "Do we actually require ordering?"

If not:

**don't pay the complexity/performance cost of guaranteeing it.**

---

# 13. Scaling Workers

Our queue receives:

```text
10,000 messages/sec
```

Suppose one worker processes:

```text
100 messages/sec
```

Then roughly:

```text
10,000 / 100 = 100 workers
```

But we shouldn't permanently run exactly 100 workers.

We monitor:

```text
Queue depth
Queue age
Messages/sec
Worker utilization
Processing latency
Error rate
```

Example:

```text
Queue depth increasing
        ↓
Workers cannot keep up
        ↓
Scale workers horizontally
```

If:

```text
Queue depth decreasing
```

we can scale down.

---

# 14. Queue Depth Alone Isn't Enough

Suppose:

```text
Queue depth = 10,000
```

Sounds bad.

But if:

```text
100 workers
100 msg/sec each
```

then:

```text
capacity = 10,000 msg/sec
```

The queue can drain quickly.

Instead:

```text
Queue depth
+
Message age
+
Processing rate
```

gives us a much better picture.

For notifications, **oldest message age** is particularly useful.

Example:

```text
Oldest message age = 2 seconds
```

Fine.

But:

```text
Oldest message age = 10 minutes
```

means users are experiencing significant delay.

---

# 15. Monitoring

A production notification system should expose metrics such as:

### API

```text
request rate
error rate
latency
```

### Queue

```text
queue depth
oldest message age
enqueue rate
dequeue rate
DLQ count
```

### Workers

```text
active workers
CPU
memory
processing latency
failure rate
retry count
```

### Providers

```text
success rate
failure rate
429 rate
latency
```

This allows us to distinguish:

```text
Provider problem
```

from:

```text
Our worker problem
```

from:

```text
Queue backlog
```

At this point, I'd draw the system like this in an interview:

```text
                         ┌───────────────┐
                         │ Email Provider│
                         └───────▲───────┘
                                 │
                         ┌───────┴───────┐
                         │ Email Workers │
                         └───────▲───────┘
                                 │
Client                          Queue
  │                              │
  ▼                              │
Load Balancer                    │
  │                              │

  │                              │
  │                              │

  │                       │             │
```

```text
Workers

  ├── Rate limiting
  ├── Retry + exponential backoff
  ├── Jitter
  ├── ACK after successful processing
  └── DLQ after retry exhaustion
```

# Senior-Level Failure Scenarios

You should now be able to walk through these.

### Scenario 1 — Worker crashes

```text
Worker receives message
↓
Worker crashes
```

Answer:

> Queue doesn't receive ACK → message becomes available again → another worker processes it → idempotency prevents duplicate side effects.

---

### Scenario 2 — Provider is down

```text
Worker → Provider ❌
```

Answer:

> Retry transient failures with exponential backoff and jitter. Don't retry permanently invalid requests. After the retry limit, move the message to DLQ.

---

### Scenario 3 — SMS provider limits us to 1k/sec

Answer:

> Rate-limit outgoing provider calls. Queue absorbs excess traffic while workers process at the allowed rate.

---

### Scenario 4 — SMS provider is down for 30 minutes

The interesting question:

> Should we continue retrying everything immediately?

No.

Otherwise:

```text
10,000,000 messages
        ↓
mass retries
        ↓
provider recovers
        ↓
massive traffic spike
```

Better:

```text
Queue
 ↓
controlled retries
 ↓
backoff + jitter
 ↓
rate-limited workers
```

Potentially isolate SMS into its own queue so email/push remain healthy.

## Notification System — Senior Interview Cheat Sheet

```text
Queue
  ↓
Workers
  ↓
Idempotency
  ↓
Rate Limit
  ↓
Provider
```

**Delivery:**
At-least-once → duplicates are possible.

**Duplicate protection:**
Idempotency key/state.

**ACK:**
ACK only after successful processing.

**Worker crash:**
No ACK → message redelivered.

**Retry:**
Only transient failures.

**Retry strategy:**
Exponential backoff + jitter.

**Permanent failure:**
DLQ.

**Provider limits:**
Rate limiting.

**Ordering:**
Only introduce when business requirements need it.

**Scaling:**
Scale workers based on queue depth, message age, processing rate and worker utilization.

**Isolation:**
Separate queues when workloads need independent scaling/failure isolation.

**Consistency:**
Don't claim exactly-once unless the entire side-effect chain actually supports it.
