## First: What are we actually building?

Imagine an app like Uber, Amazon, or a banking app.

The application wants to send a message to a user:

```text
"Your order has been shipped."
```

But it could be sent through:

* Email
* SMS
* Push notification

Our API is:

```text
POST /notifications
```

The request might look like:

```json
{
  "userId": "user_123",
  "type": "SMS",
  "message": "Your order has been shipped."
}
```

The system's job is simply:

> **Receive the request and eventually deliver the notification.**

---

# Why can't the API just send the SMS directly?

The naive design is:

```text
Client
   ↓
API
   ↓
SMS Provider
   ↓
User
```

Seems easy.

But remember our requirement:

```text
10,000 requests/sec
```

And the SMS provider can take:

```text
1–3 seconds
```

Imagine 10,000 users request notifications at the same time.

The API servers would be sitting around waiting:

```text
API #1
 ├── waiting for SMS
 ├── waiting for SMS
 ├── waiting for SMS
 └── ...

API #2
 ├── waiting for SMS
 └── ...
```

That's bad.

---

# So we introduce a Queue

Instead:

```text
Client
   ↓
API
   ↓
Queue
   ↓
Worker
   ↓
SMS Provider
   ↓
User
```

The important idea is:

### API doesn't send the SMS.

It just says:

> "I've received your request. I'll put the work in the queue."

Then the worker handles it later.

---

# Think of the Queue Like a Waiting Line

Imagine a restaurant.

Customers arrive:

```text
Customer 1
Customer 2
Customer 3
Customer 4
Customer 5
...
```

They don't all need to be served immediately by the same waiter.

They enter a queue:

```text
┌─────────────────────────────┐
│ Customer 1                  │
│ Customer 2                  │
│ Customer 3                  │
│ Customer 4                  │
│ Customer 5                  │
└─────────────────────────────┘
```

Workers are waiters:

```text
             Queue
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
    Worker1 Worker2 Worker3
```

Each worker takes a job.

For us:

```text
Notification 1 → Worker 1
Notification 2 → Worker 2
Notification 3 → Worker 3
```

---

# Why Do We Need Workers?

Because sending the notification is the **slow part**.

Our API should be fast:

```text
Client
  ↓
API
  ↓
Queue
  ↓
"Accepted"
```

Then separately:

```text
Queue
  ↓
Worker
  ↓
SMS provider
```

So the user doesn't have to wait 1–3 seconds for the provider.

---

# Now Let's Understand the Failure Problem

Suppose:

```text
Queue
  ↓
Worker
  ↓
SMS Provider
  ↓
User
```

Worker gets:

```text
Notification #123
```

It sends:

```text
"Your order has shipped"
```

SMS provider says:

```text
SUCCESS
```

So the user receives the SMS.

But then:

```text
Worker crashes
```

Before the worker can tell the queue:

> "I'm done."

The queue thinks:

> "Worker didn't finish this job."

So it gives notification #123 to another worker:

```text
Queue
  ↓
Worker 2
  ↓
SMS Provider
  ↓
User
```

Now the user could receive:

```text
Your order has shipped.

Your order has shipped.
```

That's the problem we're trying to solve.

---

# What Is ACK?

ACK simply means:

> **"I successfully finished processing this message."**

Think of a worker receiving a package.

```text
Queue:
"Here's package #123."

Worker:
"I'll process it."

Worker successfully finishes.

Worker → Queue:
"ACK — I'm done."
```

The queue can then remove the message.

If the worker dies before ACK:

```text
Queue
 ↓
Worker
 ↓
💥 crash
```

No ACK.

So the queue says:

> "Nobody finished this."

And gives it to another worker.

---

# Why Do We Need Idempotency?

Because the queue can give us the same notification again.

For example:

```text
Notification #123
       ↓
Worker 1
       ↓
SMS sent
       ↓
Worker crashes
       ↓
Queue retries #123
       ↓
Worker 2
```

Worker 2 needs to know:

> "Has notification #123 already been processed?"

So we maintain a record:

```text
notification_id | status
-------------------------
123              | SENT
```

Worker 2 checks:

```text
Is #123 already SENT?

YES
 ↓
Don't send again
 ↓
ACK
```

That's the basic idea of **idempotency**.

---

# The Complete Picture

Don't worry about separate queues, rate limiting, DLQs, Redis, etc. yet.

For now, understand this:

```text
                    ┌──────────────┐
                    │ SMS Provider │
                    └──────▲───────┘
                           │
                           │
Client                     │
  │                        │
  ▼                        │
API ──────► Queue ─────► Worker
                           │
                           ▼
                       Database
                    notification status
```

The flow is:

### 1. Client

```text
"Send SMS to Aashir"
```

↓

### 2. API

```text
Create notification
Put job in queue
```

↓

### 3. Queue

```text
"Send notification #123"
```

↓

### 4. Worker

```text
Take #123
```

↓

### 5. Worker checks database

```text
#123 already SENT?
```

If yes:

```text
Don't send
ACK
```

If no:

```text
Send SMS
```

↓

### 6. SMS Provider

```text
SUCCESS
```

↓

### 7. Worker

```text
Mark #123 as SENT
ACK queue message
```

---

# The One Thing I Want You to Understand First

Forget the advanced stuff for a moment.

The core reason for the architecture is:

```text
API = accept the work quickly

Queue = hold the work

Worker = perform the slow work
```

And the core reliability problem is:

```text
Worker can crash
      ↓
Queue can retry
      ↓
Same notification may be processed twice
      ↓
Idempotency prevents duplicate processing
```

That's it.

Once this mental model is solid, **then** we'll add retries, DLQ, rate limits, ordering, worker scaling, etc. one at a time.
