# Notification System — Interview Learning Version

## 0. What are we building?

A system that sends notifications to users through:

* Push notifications
* SMS
* Email

The most important idea:

> **Accept the request quickly, then deliver the notification asynchronously.**

Basic architecture:

```text
Trigger
   ↓
Notification API
   ↓
Queue
   ↓
Worker
   ↓
Provider
   ↓
User
```

Example:

```text
Order Service
     ↓
"Order shipped"
     ↓
Notification API
     ↓
Queue
     ↓
Worker
     ↓
Email/SMS/Push Provider
     ↓
Customer
```

The API should **not wait for the provider to deliver the notification**.

---

# 1. Why not call the provider directly?

Naive design:

```text
Order Service
     ↓
Notification API
     ↓
SMS Provider
     ↓
User
```

Suppose the SMS provider takes 2 seconds.

Every request now has to wait:

```text
Request
  ↓
API
  ↓
wait 2 sec
  ↓
Provider response
  ↓
Response to client
```

At high traffic, API servers spend a lot of time waiting on an external service.

There's another problem:

```text
Provider ❌
     ↓
Notification API ❌
     ↓
Your system is affected
```

Your notification system becomes tightly coupled to the provider's availability.

---

# 2. Add a Queue

Better:

```text
Notification API
       ↓
     Queue
       ↓
    Worker
       ↓
   Provider
```

Now:

```text
Client
  ↓
API
  ↓
"Accepted"
```

The API doesn't wait for the actual delivery.

The worker handles the slow operation separately.

### Think of a restaurant

Without a queue:

```text
Customer → Waiter → Kitchen → Wait → Food
```

With a queue:

```text
Customer → Order Queue → Kitchen → Food
```

The waiter doesn't stand there waiting for the kitchen.

That's basically what we're doing.

---

# 3. What does the Queue actually solve?

A queue gives us **buffering**.

Suppose suddenly:

```text
1,000 requests/sec
        ↓
     Queue
        ↓
    Workers
```

Workers can process the notifications at their own rate.

If traffic temporarily spikes:

```text
        Queue
      ↙  ↓  ↘
   10k  20k  30k
```

The requests don't all have to be processed immediately by the API.

### Queue = waiting room for work

That's the mental model to remember.

---

# 4. The Important Failure: Duplicate Notifications

Now we have:

```text
Queue
  ↓
Worker
  ↓
Provider
```

Suppose the worker sends notification `123`.

```text
Worker
   ↓
Provider
   ↓
SUCCESS
   ↓
User receives SMS
```

But before the worker acknowledges the queue message:

```text
Worker 💥 crashes
```

The queue doesn't know that the provider already succeeded.

So it gives the message to another worker:

```text
Queue
  ↓
Worker 2
  ↓
Provider
  ↓
User receives SMS AGAIN ❌
```

This is extremely important.

### Queue does NOT guarantee exactly-once processing.

Most queue systems are designed around:

> **At-least-once delivery**

Meaning:

```text
Message → delivered at least once
```

But potentially:

```text
Message → delivered twice
```

---

# 5. Idempotency

Now we introduce the solution.

Give every notification a unique ID:

```text
notification_id = 123
```

Store its status:

```text
notification_id | status
-------------------------
123             | SENT
124             | PENDING
125             | FAILED
```

Worker receives:

```text
notification_id = 123
```

It checks:

```text
Is notification 123 already SENT?
```

If yes:

```text
Skip sending
      ↓
ACK queue message
```

If not:

```text
Send
 ↓
Mark SENT
 ↓
ACK
```

### Mental model

```text
Queue
  ↓
At-least-once
  ↓
Duplicates possible
  ↓
Idempotency
  ↓
Prevent duplicate side effects
```

This is one of the most important concepts in the entire system.

---

# 6. But there's a tricky problem

You might think:

```text
1. Send notification
2. Mark SENT
3. ACK queue
```

But what if:

```text
1. Send notification ✅
2. Mark SENT ❌
```

The worker crashes between those operations.

The notification was already sent, but the DB still says:

```text
PENDING
```

The message gets retried.

This is why distributed systems often cannot simply promise:

> "We'll send it exactly once."

Instead, we usually design for:

```text
At-least-once processing
        +
Idempotency
        +
careful state management
```

And where possible, the provider itself should support an idempotency key.

---

# 7. Basic Architecture

Now our system becomes:

```text
                     ┌──────────────┐
Trigger ──→ API ──→  │    Queue     │
                     └──────┬───────┘
                            ↓
                         Worker
                            ↓
                     Check notification
                            ↓
                    Provider Adapter
                            ↓
                     SMS / Email / Push
                            ↓
                          User
```

Database:

```text
Notification DB
       ↑
       │
    Worker
```

The DB stores things like:

```text
notification_id
user_id
channel
status
created_at
attempt_count
```

---

# 8. What if the Provider is Down?

Suppose:

```text
Worker
   ↓
SMS Provider ❌
```

We shouldn't immediately mark the notification as permanently failed.

The failure might be temporary.

So we retry.

```text
Attempt 1 ❌
    ↓
wait
    ↓
Attempt 2 ❌
    ↓
wait longer
    ↓
Attempt 3 ❌
```

This is:

> **Exponential backoff**

Example:

```text
1 sec
2 sec
4 sec
8 sec
16 sec
```

Usually add **jitter** so thousands of workers don't retry at exactly the same time.

---

# 9. What if it keeps failing?

Don't retry forever.

After some number of attempts:

```text
Worker
  ↓
Retry 1 ❌
  ↓
Retry 2 ❌
  ↓
Retry 3 ❌
  ↓
DLQ
```

### DLQ = Dead Letter Queue

It stores messages that couldn't be successfully processed.

Why?

Because otherwise:

```text
Bad notification
      ↓
retry forever
      ↓
consume worker capacity
      ↓
hurt healthy notifications
```

DLQ gives us:

```text
Failed message
      ↓
Isolated
      ↓
Investigate / retry manually
```

---

# 10. What if the Provider is Completely Down?

Imagine:

```text
                    ┌→ Provider A ❌
Worker ─────────────┤
                    └→ Provider B
```

We can have a **backup provider**.

For example:

```text
Worker
  ↓
Primary Provider
  ↓
Repeated failures
  ↓
Circuit Breaker
  ↓
Secondary Provider
```

### Circuit breaker

Instead of continuously doing:

```text
try
try
try
try
try
try
```

we say:

```text
Provider appears unhealthy
        ↓
OPEN circuit
        ↓
Stop sending requests there
        ↓
Use fallback
```

This protects our system from repeatedly hammering a broken dependency.

---

# 11. Priority Notifications

Imagine we have:

```text
1,000,000 marketing notifications
```

and at the same time:

```text
Password reset OTP
```

If everything goes into one queue:

```text
Queue
│
├── marketing
├── marketing
├── marketing
├── ...
├── OTP ← waiting
```

The OTP could be delayed.

That's bad.

So we separate workloads:

```text
                 Notification API
                       ↓
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          HIGH       MEDIUM      LOW
           ↓           ↓          ↓
        Workers      Workers    Workers
           ↓           ↓          ↓
         OTP       Transaction  Marketing
```

### Important

It's not enough to simply put a `priority` field on messages if all workers share the same capacity.

We want **isolated worker capacity** for critical traffic.

---

# 12. User Preferences

Suppose:

```text
10:00 AM
User allows marketing emails

10:01 AM
Notification queued

10:02 AM
User disables marketing

10:05 AM
Worker processes notification
```

If we only checked preferences at enqueue time:

```text
10:01 → allowed ✅
10:05 → send ❌
```

The preference is now stale.

So:

```text
Enqueue
   ↓
Check preferences
   ↓
Queue
   ↓
Worker
   ↓
Check preferences AGAIN
   ↓
Send
```

This costs an additional read, but prevents sending notifications that the user has just opted out of.

---

# 13. Multiple Devices

A user might have:

```text
User 123
 ├── iPhone
 ├── Android tablet
 └── Web browser
```

One notification event:

```text
"Your order shipped"
```

may need to reach multiple devices.

Maintain a device registry:

```text
user123
   ↓
[token A, token B, token C]
```

Then:

```text
Notification
      ↓
Device Registry
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
 A    B    C
```

We still consider this **one notification event**, rather than creating unrelated notification records for every device.

If a provider says:

```text
token B = invalid
```

remove/prune that device token.

---

# 14. Capacity Estimation

Suppose:

```text
100M users
×
2 notifications/day
=
200M notifications/day
```

Average:

```text
200M / 86,400
≈ 2,315 notifications/sec
```

If peak traffic is 5× average:

```text
≈ 11,500 notifications/sec
```

Now suppose one worker takes:

```text
200 ms
```

That's:

```text
0.2 sec
```

Approximate concurrent workers:

```text
11,500 × 0.2
≈ 2,300
```

This isn't the final production number.

It's a **starting estimate**.

Then we validate with load testing.

### Important formula

```text
Workers ≈ Peak QPS × Processing Time
```

# 15. Final Architecture

Now we can put everything together:

```text
                  ┌───────────────┐
                  │ Trigger       │
                  │ Services      │
                  └───────┬───────┘
                          ↓
                    Notification API
                          ↓
              ┌───────────┼───────────┐
              ↓           ↓           ↓
           HIGH         MEDIUM        LOW
           Queue        Queue         Queue
              ↓           ↓           ↓
          Workers      Workers      Workers
              │           │           │
              └───────────┼───────────┘
                          ↓
                 Preference Check
                          ↓
                  Provider Adapter
                    /          \
                   ↓            ↓
              Provider A    Provider B
                   ↓            ↓
                   └─────┬──────┘
                         ↓
                        User

                         ↕
                  Notification DB
                  (status / IDs)

Failures:
    ↓
 Retry + Backoff
    ↓
   DLQ
```

# 16. The 30-Second Interview Answer

If an interviewer says:

> "Design a notification system."

You don't need to immediately dump all the components.

Start here:

> "I'd decouple notification creation from delivery. The API would validate the request, create a notification ID, and put the notification onto a queue. Workers would consume the queue and call the appropriate email, SMS, or push provider. This prevents slow or unavailable providers from blocking the API."

Then continue:

> "Because queues typically provide at-least-once delivery, I'd make the operation idempotent using the notification ID or a provider-supported idempotency key. I'd add retries with exponential backoff for transient failures and a DLQ for messages that repeatedly fail."

Then, depending on the interviewer:

> "For scale and reliability, I'd separate critical notifications such as OTPs from lower-priority marketing traffic, re-check user preferences before delivery, and use provider failover or a circuit breaker if the primary provider becomes unhealthy."

That's a **very solid senior-level progression** without unnecessarily overengineering the initial design.

## The mental model I want you to remember

```text
API
 ↓
Queue
 ↓
Worker
 ↓
Provider
 ↓
User
```

Then ask:

```text
Provider slow?
→ Queue

Duplicate?
→ Idempotency

Temporary failure?
→ Retry + backoff

Permanent failure?
→ DLQ

Critical notification delayed?
→ Priority queues + separate workers

Provider down?
→ Circuit breaker + fallback

User opted out?
→ Check preferences before sending

Multiple devices?
→ Device registry + fan-out
```
