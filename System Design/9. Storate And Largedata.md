# Day 8 — Storage & Large Data

Today we'll learn how systems handle **files and large amounts of data** without putting everything directly into a database.

The key question for today is:

> **Where should data live, and how do we efficiently store and retrieve large files?**

We'll build this from a simple system first, then add complexity only when there's a reason.

---

## 1. Start Simple: Upload a File

Imagine we're building a document-management application.

User uploads:

```text
report.pdf
```

A naive architecture:

```text
Client
   ↓
API Server
   ↓
Database
```

The API receives the entire file and stores it in the database.

This can work for small files, but becomes problematic at scale.

---

# 2. Why Not Store Large Files in the Database?

Imagine:

```text
10 million users
×
10 MB average file
```

That's:

```text
100 TB
```

Now imagine storing all of that inside your primary application database.

You have several problems:

* Database storage becomes huge.
* Backups become expensive.
* Database replication becomes heavier.
* Large uploads consume DB connections/resources.
* Application servers may have to handle unnecessary file traffic.

A database is generally better suited for **structured application data**.

For example:

```text
users
documents
orders
payments
notifications
```

rather than:

```text
video.mp4
report.pdf
image.png
backup.zip
```

---

# 3. Object Storage

This is where **object storage** comes in.

Examples include:

* Amazon S3
* Google Cloud Storage
* Azure Blob Storage

Conceptually:

```text
                ┌───────────────┐
                │ Object Storage│
                └───────┬───────┘
                        │
                    report.pdf
```

Instead of storing the file in your DB:

```text
Database
   ↓
document metadata
```

and:

```text
Object Storage
   ↓
actual file
```

---

# 4. Database + Object Storage

This is the important pattern.

```text
                 ┌──────────────┐
                 │  Application │
                 └──────┬───────┘
                        │
                ┌───────┴────────┐
                ↓                ↓
           Database        Object Storage
                ↓                ↓
         metadata only       actual file
```

For example:

### Database

```text
document_id: 123
user_id: 456
filename: report.pdf
storage_key: users/456/report.pdf
size: 10MB
created_at: ...
```

### Object storage

```text
users/456/report.pdf
        ↓
      actual bytes
```

### Easy mental model

> **Database tells you about the file. Object storage contains the file.**

---

# 5. The Upload Problem

Now suppose the user uploads a 500 MB video.

Naive approach:

```text
Client
   ↓
API Server
   ↓
Object Storage
```

The API server is now sitting in the middle of 500 MB of traffic.

If 1,000 users upload simultaneously:

```text
1,000 × 500 MB
=
500 GB
```

Your application servers become a bottleneck.

But your API isn't actually doing useful business logic.

It's just moving bytes.

---

# 6. Direct Upload

A better architecture:

```text
Client
   ↓
API
   ↓
"Here's permission to upload"
   ↓
Client
   ↓
Object Storage
```

The API doesn't transfer the file.

Instead, it gives the client a temporary URL/token that allows the upload.

This is commonly implemented using a:

> **Pre-signed URL**

---

# 7. Pre-Signed URL

Flow:

```text
Client
   ↓
POST /uploads
   ↓
API
   ↓
Generate pre-signed URL
   ↓
Client
   ↓
PUT file directly
   ↓
Object Storage
```

The actual file transfer becomes:

```text
Client ─────────────────→ Object Storage
```

instead of:

```text
Client → API → Object Storage
```

### Why is this better?

Because:

* API servers don't handle large file traffic.
* Object storage handles the upload.
* Application servers remain focused on business logic.
* It scales much better.

---

# 8. What Does the API Actually Do?

Suppose the user wants to upload:

```text
profile-photo.jpg
```

The client asks:

```text
POST /uploads
```

API:

```text
1. Authenticate user
2. Validate file type/size
3. Generate storage key
4. Generate pre-signed URL
5. Return URL
```

Response:

```json
{
  "uploadUrl": "...",
  "fileKey": "users/123/profile/photo.jpg"
}
```

Then:

```text
Client
   ↓
PUT uploadUrl
   ↓
Object Storage
```

The API never receives the actual 10 MB file.

---

# 9. But How Does the Database Know the Upload Finished?

This is where we need to think carefully.

One approach:

```text
Client
   ↓
Upload
   ↓
Object Storage
   ↓
Client tells API
   ↓
API marks file as uploaded
```

But what if:

```text
Upload succeeds
      ↓
Client crashes
      ↓
API never receives confirmation
```

Now:

```text
Object Storage → file exists
Database → says pending
```

We need a way to reconcile these states.

---

# 10. Object Storage Events

Object storage can emit an event:

```text
Object Storage
      ↓
"file uploaded"
      ↓
Event / Queue
      ↓
Worker
      ↓
Database
```

For example:

```text
Client
  ↓
Object Storage
  ↓
UploadComplete event
  ↓
Queue
  ↓
Worker
  ↓
DB → status = READY
```

Now the system can process uploaded files asynchronously.

---

# 11. Large File Processing

Suppose users upload videos.

After upload:

```text
Video uploaded
      ↓
Need processing
      ↓
Transcode
      ↓
Generate thumbnails
      ↓
Extract metadata
```

Don't make the upload request wait for all of this.

Instead:

```text
Object Storage
      ↓
Event
      ↓
Queue
      ↓
Worker
      ↓
Video Processing
```

Same principle as the notification system:

> **Move slow work off the request path.**

---

# 12. Multipart Upload

Now suppose the file is:

```text
5 GB
```

Uploading it as one giant request is risky.

Imagine:

```text
4.8 GB uploaded
      ↓
Network failure
      ↓
Upload fails ❌
```

You may have to start again.

Instead, split the file into parts:

```text
5 GB file

┌────┬────┬────┬────┬────┐
│ P1 │ P2 │ P3 │ P4 │ P5 │
└────┴────┴────┴────┴────┘
```

Upload them independently:

```text
P1 → Object Storage
P2 → Object Storage
P3 → Object Storage
P4 → Object Storage
P5 → Object Storage
```

If P4 fails:

```text
P1 ✅
P2 ✅
P3 ✅
P4 ❌
P5 ✅
```

Only retry:

```text
P4
```

This is **multipart upload**.

---

# 13. Why Multipart Upload Matters

It provides:

### Resumability

If the network fails, continue from where you stopped.

### Parallelism

```text
       ┌→ Part 1
       ├→ Part 2
File ──┼→ Part 3
       ├→ Part 4
       └→ Part 5
```

Multiple parts can upload simultaneously.

### Better reliability

A failed part doesn't necessarily require restarting the entire upload.

---

# 14. Downloading Large Files

We have the same problem in reverse.

Naive:

```text
Client
   ↓
API
   ↓
Object Storage
```

Again, the API becomes a data-transfer bottleneck.

Better:

```text
Client
   ↓
API → generate temporary download URL
   ↓
Client
   ↓
Object Storage
```

So:

```text
        API
         ↓
 authorization
         ↓
Client ─────────→ Object Storage
```

Again:

> **API handles authorization; object storage handles bytes.**

---

# 15. CDN

Now imagine a popular image:

```text
logo.png
```

10 million users request it.

If every request goes:

```text
User
  ↓
Object Storage
```

that's unnecessary.

We can introduce a CDN:

```text
User
  ↓
CDN
  ↓
Object Storage
```

First request:

```text
User
 ↓
CDN MISS
 ↓
Object Storage
 ↓
CDN stores copy
 ↓
User
```

Next request:

```text
User
 ↓
CDN HIT
 ↓
User
```

The object doesn't need to be retrieved from storage every time.

---

# 16. CDN + Object Storage

The architecture becomes:

```text
                     ┌──────────────┐
                     │      API     │
                     └──────┬───────┘
                            │
                       auth / metadata
                            │
                            ↓
Client ─────────────────→ CDN
                            ↓
                     Object Storage
```

For uploads:

```text
Client ─────────────────→ Object Storage
```

For downloads:

```text
Client → CDN → Object Storage
```

This is a very common architecture.

# 17. Storage Classes / Data Lifecycle

Not every file needs to remain in expensive, frequently accessible storage forever.

Suppose:

```text
Day 0       → frequently accessed
Day 30      → rarely accessed
Day 365     → almost never accessed
```

You can move old data into cheaper storage tiers.

Conceptually:

```text
HOT
 ↓
WARM
 ↓
COLD
 ↓
ARCHIVE
```

For example:

```text
Recent invoices
     ↓
Standard storage

Old invoices
     ↓
Archive storage
```

This is called a:

> **Data lifecycle policy**

---

# 18. Replication

What happens if an object-storage region has an outage?

You may replicate data:

```text
                 Object
                   ↓
          ┌────────┴────────┐
          ↓                 ↓
      Region A           Region B
```

Now if Region A becomes unavailable:

```text
Region A ❌
    ↓
Region B
```

But replication has trade-offs:

* additional storage cost
* replication delay
* more operational complexity

Don't automatically replicate everything across multiple regions.

Ask:

> **What availability and durability does this data actually require?**

---

# 19. Sharding vs Partitioning

These terms are often used interchangeably — "partitioning" is the general concept (splitting data across multiple nodes), and "sharding" is the specific case of partitioning applied to a database for horizontal scaling. In practice, most engineers say "sharding" when they mean database partitioning.

Suppose a database contains:

```text
10 billion records
```

One database may eventually become a bottleneck.

We can partition the data.

Example:

```text
Users

A-F → DB1
G-M → DB2
N-S → DB3
T-Z → DB4
```

The real question that matters in an interview is: **how do you decide which shard a piece of data goes to, and what happens when you add a shard?**

### The naive approach: modulo

```text
user_id % 4

0 → DB1
1 → DB2
2 → DB3
3 → DB4
```

This works — until you need a 5th shard.

```text
user_id % 4          user_id % 5
    ↓                     ↓
user_id=8 → DB1      user_id=8 → DB3   ❌ moved
user_id=9 → DB2      user_id=9 → DB4   ❌ moved
user_id=10 → DB3     user_id=10 → DB5  ❌ moved
```

Almost **every key remaps** to a different shard when you change the divisor. At scale, that means migrating nearly all your data just to add one more database.

### The fix: consistent hashing

```text
Instead of: hash(key) % N

Think of a ring of hash values, 0 to MAX, wrapping around.
Each shard owns a position on the ring.
Each key is placed on the ring by its hash, and belongs to
the NEXT shard clockwise from it.
```

```text
Ring:

        DB1
      ↗      ↘
   DB4          DB2
      ↖      ↙
        DB3

key "abc" hashes to a point between DB2 and DB3
    → belongs to DB3 (next shard clockwise)
```

Why this fixes the remapping problem:

```text
Add DB5 between DB1 and DB2 on the ring
    ↓
ONLY the keys that were between DB1 and DB5 move to DB5
    ↓
every other key's shard assignment is UNCHANGED
```

Adding or removing a shard only reshuffles the keys adjacent to that one point on the ring — not the entire keyspace.

**Interview answer:** "Naive `hash % N` sharding causes almost all keys to remap when N changes, which means a full data migration every time you scale. Consistent hashing places both shards and keys on a ring by hash value, so adding or removing a shard only affects the keys immediately adjacent to it — not the whole dataset."

### Why shard at all?

To scale:

* storage capacity
* read/write throughput
* workload

---

# 20. Partitioning vs Replication

Don't mix these up.

### Replication

Same data copied to multiple nodes.

```text
       Primary
       /     \
      ↓       ↓
 Replica   Replica
```

Purpose:

* availability
* read scaling
* disaster recovery

### Partitioning / Sharding

Different data distributed across nodes.

```text
DB1 → users 1–1M
DB2 → users 1M–2M
DB3 → users 2M–3M
```

Purpose:

* scale storage
* scale throughput

### Memory trick

```text
Replication = COPY

Partitioning = SPLIT
```

# 22. The Mental Model

You don't need to memorize all of this as separate technologies.

Remember these four rules:

```text
1. Structured data
       ↓
   Database

2. Large files
       ↓
   Object Storage

3. Large file transfer
       ↓
   Direct upload/download

       ↓
   CDN
```

And:

```text
Slow processing
      ↓
Queue + Worker
```

# Senior Interview Questions

### Q1. Why not store a 1 GB video directly in PostgreSQL?

> It bloats the database's storage, makes backups and replication dramatically heavier, and consumes DB connections/resources for traffic that isn't even structured data. Databases are optimized for structured, queryable records — not raw byte blobs. Object storage is purpose-built for files; the database should only hold metadata about them.

### Q2. Why shouldn't the API server handle every large file upload?

> The API server would sit in the middle of the byte stream for no reason — it isn't doing business logic, just relaying data. At scale (1,000 concurrent 500MB uploads = 500GB through your app servers), this becomes the bottleneck and wastes compute that should be handling requests, not moving files. A direct client → object storage upload removes the API from the data path entirely.

### Q3. What is a pre-signed URL?

> A temporary, scoped URL the API generates that grants permission to upload or download a specific object directly from storage, without the client needing real credentials. It typically expires after a short window and can be scoped to a specific key, content-type, and size limit — so a leaked URL has a small blast radius.

### Q4. How would you upload a 10 GB file reliably?

> Multipart upload — split the file into chunks (e.g. 5-10MB each), upload each part independently (possibly in parallel), and let object storage reassemble them once all parts arrive. This makes the upload resumable (retry only the failed part, not the whole file) and parallelizable.

### Q5. What happens if an upload fails at 90%?

> With multipart upload, only the failed part needs to be retried — the other 90% already succeeded and is stored. Without multipart (one giant request), the entire upload must restart from zero, which is why single-request uploads don't scale to large files.

### Q6. Why use a CDN in front of object storage?

> A CDN caches frequently-requested objects at edge locations close to users, so repeat requests for the same file (e.g. a popular image) don't have to travel back to origin storage every time. It reduces latency for users and reduces load/cost on the origin store.

### Q7. What's the difference between replication and sharding?

> Replication copies the *same* data to multiple nodes — for availability, read scaling, and disaster recovery. Sharding splits *different* data across multiple nodes — for scaling storage capacity and write throughput. Memory trick: replication = COPY, sharding = SPLIT.

### Q8. A user uploads a file successfully, but your database still says `PENDING`. How could that happen, and how would you solve it?

> The client likely crashed or lost connectivity after the upload succeeded but before it could call the API to confirm completion — so the object exists in storage but the DB was never updated. The fix is not relying on the client to report success: have object storage emit an event on upload completion (e.g. S3 event notifications), push it to a queue, and have a worker update the DB to READY based on that event instead of a client callback.
