# Day 5 — Rate Limiting

We'll start very simple and gradually make it Senior-level.

---

## 1. What problem does Rate Limiting solve?

Imagine we have an API:

```text
POST /login
```

Normally:

```text
User → API
```

A user might make:

```text
5 requests/sec
```

But what if someone sends:

```text
10,000 requests/sec
```

to our API?

```text
Attacker
   │
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   └── ... 10,000/sec
          ↓
        API
```

Our API could become overloaded.

So we need a mechanism that says:

> **"You are allowed to make only X requests within a certain period."**

That's **rate limiting**.

---

# 2. Simple Example

Suppose we define:

```text
100 requests / minute / user
```

User A:

```text
Request 1  ✅
Request 2  ✅
...
Request 100 ✅
Request 101 ❌
```

The API returns something like:

```text
HTTP 429 Too Many Requests
```

So:

```text
User
 ↓
API
 ↓
Rate Limiter
 ├── allowed → continue
 └── exceeded → 429
```

---

# 3. Why Do We Need It?

There are several reasons.

### Protect the API

```text
Too many requests
       ↓
API overload
       ↓
High latency
       ↓
System failure
```

### Protect expensive operations

For example:

```text
POST /generate-report
```

might be expensive.

We don't want one user generating:

```text
10,000 reports/sec
```

### Protect third-party providers

This connects directly to our notification system.

Suppose:

```text
SMS Provider limit = 1,000 requests/sec
```

but our workers can generate:

```text
5,000 requests/sec
```

We need rate limiting before the provider.

```text
Workers
   ↓
Rate Limiter
   ↓
1,000/sec
   ↓
SMS Provider
```

---

# 4. Where Can Rate Limiting Exist?

This is important.

It can happen at different levels.

### API Gateway

```text
Client
  ↓
API Gateway
  ↓
API Servers
```

The gateway can reject excessive requests before they reach our application.

### Application

```text
Client
  ↓
API
  ↓
Rate Limiter
  ↓
Business Logic
```

Useful when the limit depends on application-specific information.

### Worker/provider side

```text
Queue
  ↓
Workers
  ↓
Rate Limiter
  ↓
Third-party API
```

Useful for protecting external providers.

---

# 5. Per-User vs Global Limits

This is a very important distinction.

Suppose we have:

```text
100 requests/sec
```

### Global limit

The **entire system** can process 100 requests/sec.

```text
User A ─┐
User B ─┼──► 100/sec total
User C ─┘
```

If User A consumes all 100:

```text
User A → 100/sec
User B → blocked
User C → blocked
```

Probably not what we want for a public API.

---

### Per-user limit

Instead:

```text
100 requests/sec/user
```

Then:

```text
User A → 100/sec
User B → 100/sec
User C → 100/sec
```

Much more fair.

---

# 6. Different Users May Have Different Limits

Real systems often have tiers.

For example:

```text
Free       → 10 req/sec
Pro        → 100 req/sec
Enterprise → 1,000 req/sec
```

So the rate limiter might look at:

```text
User
 ↓
Plan
 ↓
Rate limit
```

---

# 7. First Algorithm: Fixed Window

Let's start with the easiest algorithm.

Suppose:

```text
100 requests / minute
```

We create a counter:

```text
user_123 : 37
```

Every request:

```text
counter++
```

When it reaches:

```text
100
```

we reject further requests.

At the beginning of the next minute:

```text
counter = 0
```

Diagram:

```text
12:00 ───────────────── 12:01
      100 requests max

12:01 ───────────────── 12:02
      100 requests max
```

This is called:

**Fixed Window Rate Limiting.**

---

# 8. Problem With Fixed Windows

Here's the interesting part.

Suppose limit:

```text
100 requests/minute
```

User sends:

```text
12:00:59 → 100 requests
```

Then:

```text
12:01:00 → 100 requests
```

The system accepted:

```text
200 requests
```

within approximately:

```text
2 seconds
```

even though the intended limit was:

```text
100/minute
```

This is called a **boundary problem**.

---

# 9. Sliding Window

Instead of fixed calendar windows, we consider a moving period.

For example:

> Look at the previous 60 seconds.

At:

```text
12:01:30
```

we ask:

```text
How many requests did this user make
between 12:00:30 and 12:01:30?
```

If:

```text
< 100 → allow
≥ 100 → reject
```

More accurate, but potentially more expensive to implement.

---

# 10. Token Bucket ⭐

This is one you should definitely understand for interviews.

Imagine a bucket:

```text
       ┌─────────────┐
       │ 🟠 🟠 🟠 🟠 │
       │ 🟠 🟠 🟠    │
       └─────────────┘
```

The bucket can hold:

```text
10 tokens
```

Tokens are added at a fixed rate.

For example:

```text
1 token/sec
```

Each request consumes one token.

```text
Request
   ↓
Take 1 token
   ↓
Token available?
 ┌───────┴───────┐
 YES             NO
  ↓               ↓
Allow            Reject
```

---

# 11. Why Is Token Bucket Useful?

Because it allows **small bursts**.

Suppose:

```text
Bucket capacity = 10
Refill = 1 token/sec
```

If nobody makes requests for a while:

```text
10 tokens available
```

The user can make:

```text
10 requests quickly
```

Then they're limited by:

```text
1 new request/sec
```

This is often more practical than simply saying:

```text
Exactly 1 request every second
```

---

# 12. Where Does Redis Come In?

Now we're getting into distributed systems.

Suppose we have:

```text
          Load Balancer
          /     |     \
         ↓      ↓      ↓
      API 1   API 2   API 3
```

If rate-limit counters live only in API server memory:

```text
API 1:
user_123 = 90

API 2:
user_123 = 5
```

The user could bypass the intended limit simply because requests hit different servers.

We need shared state.

```text
API 1 ─┐
API 2 ─┼──► Redis
API 3 ─┘
```

Redis can maintain the counter/token state.

This is one legitimate reason to introduce Redis.

---

# 13. Important Mental Model

Don't think:

> "Rate limiting = Redis."

Instead:

> **Rate limiting needs shared state when multiple application instances must enforce the same limit. Redis is one common way to provide that shared state.**

That's a much better Senior-level explanation.

---

# 14. What Happens When Limit Is Exceeded?

Usually:

```text
HTTP 429
Too Many Requests
```

We can also tell the client when to retry:

```text
Retry-After: 30
```

So the client can understand:

> Try again in 30 seconds.

---

# 15. Rate Limiting vs Throttling

For interviews, keep this simple.

### Rate limiting

Controls:

> **How many requests are allowed in a period.**

Example:

```text
100 req/min
```

### Throttling

More broadly means:

> **Slowing/restricting processing when demand exceeds capacity.**

For example:

```text
10,000 jobs/sec incoming
       ↓
Workers only process
2,000/sec
       ↓
Queue absorbs the rest
```

Our notification system actually uses both concepts:

```text
API
 ↓
Rate limiting
 ↓
Queue
 ↓
Workers
 ↓
Provider rate limiting
```

---

# 16. The Architecture You Should Remember

For a normal API:

```text
Client
  ↓
Load Balancer
  ↓
Rate Limiter
  ↓
API Servers
  ↓
Database
```

For a distributed application:

```text
             ┌── API 1 ──┐
Client ─────►├── API 2 ──┼──► Redis
             └── API 3 ──┘
```

Redis stores the shared rate-limit state.

For our notification system:

```text
API
 ↓
Queue
 ↓
Workers
 ↓
Rate Limiter
 ↓
SMS Provider
```

# Interview Cheat Sheet

### Rate limiting

> Restrict how frequently a client can perform an operation.

### Why?

- Protect APIs
- Prevent abuse
- Protect expensive resources
- Protect third-party providers

### Common algorithms

```text
Fixed Window
Sliding Window
Token Bucket
```

### Distributed system

```text
Multiple API servers
       ↓
Shared rate-limit state
       ↓
Redis
```

### Exceeded limit

```text
HTTP 429
```

### Senior-level consideration

> Choose the algorithm based on the required accuracy, burst behavior, implementation complexity, and scale.
