# Day 7 — Networking & Traffic

Think of this day as answering:

> **"A user enters `https://example.com` — what happens between their browser and my application?"**

We'll build that understanding step by step.

---

## 1. DNS

When the user enters:

```text
https://example.com
```

The browser needs to find the server's IP address.

Conceptually:

```text
Browser
   ↓
DNS
   ↓
IP address
   ↓
203.0.113.10
```

DNS maps:

```text
example.com → IP address
```

### Why do we need DNS?

Because users shouldn't need to remember:

```text
203.0.113.10
```

They remember:

```text
example.com
```

### Important system-design point

DNS can also help with:

* routing users to different regions
* failover
* load distribution
* geographic routing

For example:

```text
                 DNS
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
   US Servers          Europe Servers
```

But DNS isn't a replacement for a load balancer.

---

# 2. Load Balancer

Suppose we have:

```text
              Load Balancer
             /      |      \
            ↓       ↓       ↓
          API1     API2     API3
```

Instead of the client deciding which server to call, the load balancer distributes traffic.

### Why?

Because one server might receive:

```text
100,000 requests
```

while another receives:

```text
100 requests
```

The LB tries to distribute traffic more appropriately.

---

## Common strategies

### Round robin

```text
Request 1 → API1
Request 2 → API2
Request 3 → API3
Request 4 → API1
```

Simple.

### Least connections

Send the request toward the server currently handling fewer connections.

Useful when requests have different processing times.

### Weighted routing

```text
API1 → weight 3
API2 → weight 1
```

API1 receives more traffic.

Useful when servers have different capacities.

---

# 3. Health Checks

What if API2 crashes?

```text
              LB
           /  |  \
          ↓   ↓   ↓
        API1 API2 API3
             ❌
```

The load balancer should detect that API2 is unhealthy.

For example:

```text
GET /health

200 OK
```

If API2 stops responding:

```text
API2 → unhealthy
```

The LB stops sending new traffic there.

```text
              LB
             /   \
            ↓     ↓
          API1   API3

          API2 ❌
```

### Important distinction

A health check doesn't prevent failure.

It allows the system to **stop routing traffic toward a failed instance**.

---

# 4. Reverse Proxy

This is an important concept for you because you'll encounter it frequently with **Nginx**, Next.js, APIs, etc.

Without a reverse proxy:

```text
Client
   ↓
API Server
```

With one:

```text
Client
   ↓
Reverse Proxy
   ↓
API Server
```

The reverse proxy receives the request **on behalf of the backend**.

It can handle things like:

* TLS termination
* routing
* compression
* headers
* authentication-related gateway logic
* rate limiting
* forwarding traffic

Example:

```text
example.com/
       ↓
     Nginx
    ↙     ↘
Next.js   API
```

---

# 5. Load Balancer vs Reverse Proxy

These are often confused.

They're related but not necessarily the same thing.

### Load balancer

Main concern:

> Which server should receive this traffic?

```text
          LB
       /  |  \
      ↓   ↓   ↓
     API API API
```

### Reverse proxy

Main concern:

> Act as an intermediary between client and backend.

```text
Client
   ↓
Proxy
   ↓
Backend
```

One component can perform **both roles**.

For example:

```text
Internet
   ↓
Nginx / LB
   ↓
API1 / API2 / API3
```

---

# 6. L4 vs L7 Load Balancing

This is a common interview question.

## L4

Layer 4 = transport layer.

Usually operates around:

```text
TCP / UDP
```

It doesn't need to understand HTTP details.

Conceptually:

```text
Client
  ↓
L4 LB
  ↓
TCP connection
  ↓
Server
```

It can make decisions based on things like:

* IP
* port
* TCP connection

### Advantage

Generally simpler and lower overhead.

---

## L7

Layer 7 = application layer.

It understands protocols such as HTTP.

Therefore it can inspect:

```text
HTTP method
Host
Path
Headers
Cookies
```

For example:

```text
/api/users
      ↓
   API service

/images
      ↓
Image service
```

So:

```text
             L7 LB
               ↓
       ┌───────┴────────┐
       ↓                ↓
   /api/*            /images/*
       ↓                ↓
    API servers      Image servers
```

### Easy memory trick

```text
L4 → "connection"
L7 → "request"
```

# 7. TLS / HTTPS

When you use:

```text
https://example.com
```

HTTPS provides encrypted communication between the client and server.

Without encryption, someone positioned on the network could potentially inspect traffic.

With TLS:

```text
Browser
   │
   │ encrypted
   ↓
Server
```

You don't normally want application servers individually managing public TLS certificates at large scale.

Often:

```text
Client
   ↓ HTTPS
Load Balancer
   ↓ HTTP/internal TLS
API Servers
```

The LB terminates TLS.

This is called:

> **TLS termination**

# 8. HTTP Request Lifecycle

Now combine what we've learned.

A simplified request:

```text
Browser
   ↓
DNS
   ↓
Load Balancer
   ↓
Reverse Proxy
   ↓
API Server
   ↓
Database
```

For example:

```text
GET /users/123
```

The server responds:

```text
200 OK

{
  "id": 123,
  "name": "Aashir"
}
```

---

# 9. Stateless API Servers

Suppose:

```text
              LB
          /    |    \
         ↓     ↓     ↓
       API1   API2   API3
```

A request might go:

```text
Request 1 → API1
Request 2 → API3
Request 3 → API2
```

This works well if the servers are **stateless**.

Meaning API1 doesn't have some critical session state that only API1 knows about.

Instead:

```text
API1 ─┐
API2 ─┼──→ Shared DB / Redis
API3 ─┘
```

This makes horizontal scaling much easier.

---

# 10. Sticky Sessions

Sometimes applications maintain connection/session state on a particular server.

Then the LB might use:

```text
User A → API2

User A's next request → API2
```

This is called a **sticky session**.

Problem:

```text
API2 crashes
   ↓
User loses connection/state
```

It also makes scaling and failover more complicated.

Therefore, when possible:

> Prefer stateless servers and external/shared state.

---

# 11. WebSockets

Now we reach realtime communication.

Normal HTTP:

```text
Client → Server
        ← Response
```

The connection isn't designed as a continuously interactive channel.

WebSocket establishes a persistent connection:

```text
Client
   ⇅
WebSocket Server
```

Both sides can send messages.

Example:

```text
Driver
   ↓
{lat: 43.59, lng: -79.64}

       ⇅

Customer
   ↑
location update
```

This is useful for:

* chat
* live tracking
* multiplayer games
* realtime dashboards
* collaborative editing

---

# 12. SSE

Server-Sent Events are different.

```text
Client
   ↓ request

Server
   ↓
   ↓
   ↓
updates
```

Communication is primarily:

```text
Server → Client
```

Example:

```text
Server
  ↓ "Order shipped"
  ↓ "Driver assigned"
  ↓ "Driver nearby"
```

The client doesn't get the same bidirectional channel that WebSockets provide.

### Memory trick

```text
WebSocket → ⇄
SSE       → →
```

---

# 13. Polling

The simplest approach:

```text
Client → "Where is driver?"
Server → location

wait 5 sec

Client → "Where is driver?"
Server → location

wait 5 sec
...
```

This is easy but potentially wasteful.

If the location hasn't changed:

```text
Client → request
Server → same location
```

You've still consumed:

* network bandwidth
* server processing
* database/cache reads

---

# 14. Long Polling

A middle ground.

Client asks:

```text
"Do you have an update?"
```

Instead of immediately responding:

```text
Server
   ↓
wait...
   ↓
new update
   ↓
response
```

Then the client opens another request.

Better than aggressive polling, but still more cumbersome than a persistent realtime connection.

---

# 15. WebSocket Scaling Problem ⭐

This is where system design becomes interesting.

Imagine:

```text
              Load Balancer
             /     |      \
            ↓      ↓       ↓
          WS1     WS2      WS3
```

Driver connects to:

```text
WS1
```

Customer connects to:

```text
WS3
```

Driver sends:

```text
location = (43.59, -79.64)
```

WS1 knows about it.

But:

```text
WS3 ❓
```

How does WS3 receive the update?

This is the **cross-server communication problem**.

---

# 16. Redis Pub/Sub

One common solution:

```text
                  Redis
                Pub/Sub
               /       \
              ↑         ↑
             WS1       WS3
              ↑         ↑
           Driver    Customer
```

Driver:

```text
Driver
  ↓
WS1
  ↓
Redis publish
  ↓
location:driver123
```

WS3 subscribes to the appropriate channel:

```text
Redis
  ↓
WS3
  ↓
Customer
```

Now WS3 can forward the location to the customer.

### Important

Redis isn't necessarily the database of record here.

It is being used as a **fast coordination/message-distribution layer**.

---

# 17. Redis Pub/Sub vs Queue

This connects directly to what you learned on Day 4.

### Queue

Usually:

```text
Producer → Queue → Worker
```

One worker processes the job.

Good for:

```text
Send email
Process image
Generate report
```

### Pub/Sub

```text
Publisher
    ↓
 Redis
  ↙ ↓ ↘
S1 S2 S3
```

Multiple subscribers can receive the event.

Good for:

```text
Realtime updates
```

That's an important distinction.

---

# 18. What Happens When WebSocket Server Crashes?

Suppose:

```text
Driver
  ↓
WS3 ❌
```

The persistent WebSocket connection is broken.

The client needs to:

```text
detect disconnect
      ↓
reconnect
      ↓
load balancer
      ↓
healthy WS server
```

Potentially:

```text
Driver
   X
  WS3

Driver
   ↓
LB
   ↓
WS1
```

For realtime systems, clients commonly implement:

* reconnect
* exponential backoff
* jitter
* connection heartbeat/ping-pong

---

# 19. Heartbeats

How does the server know whether a connection is still alive?

Conceptually:

```text
Client → ping
Server → pong
```

or vice versa.

If the connection stops responding:

```text
connection dead
      ↓
remove connection
```

This prevents the system from maintaining stale connections indefinitely.

---

# 20. Connection State

Here's another senior-level consideration.

Suppose WS3 knows:

```text
customer123 → socket #456
```

That mapping is local to WS3.

If WS3 dies:

```text
customer123 → socket #456 ❌
```

The connection is gone.

After reconnect:

```text
customer123 → WS7
```

Therefore, you generally don't want critical durable application state to exist **only inside a WebSocket server's memory**.

# 21. Complete Mental Model

Now we can build the architecture progressively.

### Start

```text
Client
  ↓
LB
  ↓
API
  ↓
DB
```

Need realtime:

```text
Client
  ↓
LB
  ↓
WebSocket Server
```

Multiple WS servers:

```text
                 LB
              /  |  \
             ↓   ↓   ↓
            WS1 WS2 WS3
```

Need servers to communicate:

```text
                 Redis Pub/Sub
                /      |      \
               ↑       ↑       ↑
              WS1     WS2     WS3
```

Then:

```text
Driver
  ↓
WS1
  ↓
Redis Pub/Sub
  ↓
WS3
  ↓
Customer
```

And if WS3 crashes:

```text
Customer
   X
  WS3
   ↓
reconnect
   ↓
LB
   ↓
healthy WS server
```

That's the level of understanding I want you to reach **before Day 8**.
